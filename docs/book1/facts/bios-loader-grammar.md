# BIOS runtime-load source facts (read-only extraction; ready)

Scope: runtime owners `machine/bios/compiler/{lexer,parser,semantic,compiler}.lua`, not the linked-cartridge compiler. No builds/tests or executable proof. Source citations refer to live checkout 2026-10-18. No claim that all inputs or optimizer paths have been covered.

## Accepted lexing and grammar: established

- Names start with ASCII lowercase `a-z`, `_`, or `$`; following characters add decimal digits, not uppercase letters. Encountering an uppercase character at the next token boundary raises `upper-case identifiers are not allowed`. Lexer advances index and non-newline column by one per source-index step, and advances line only at LF. Position-unit meaning belongs to the VM string primitives (paired evidence is in root API extraction), not an assumption of UTF-8 bytes. Sources: `machine/bios/compiler/lexer.lua:50-105,307-325`.
- Whitespace is ASCII space or character codes 9 through 13. Comments start `--` and continue to LF/end of input; no long-comment scanner. Sources: `machine/bios/compiler/lexer.lua:71-74,268-285`.
- Primary expressions are identifier, number, quoted string, false/true/nil, anonymous `function (...) ... end`, and parenthesized expression. Chained suffixes support `.name`, `[expression]`, `(arguments...)`, and `:name(arguments...)`; calls require parentheses. Parenthesizing a call marks it nonexpanding. Sources: `machine/bios/compiler/parser.lua:124-244`.
- Unary operators are `-`, `&` (string ID), `not`, `#`. Binary precedence, from high to low: `* / // %`, `+ -`, `&`, comparisons (`== ~= < <= > >=`), `and`, `or`. Every binary precedence level is left associative. Sources: `machine/bios/compiler/parser.lua:91-122,246-345`.
- Statements are `if/elseif/else`, numeric `for name = start,limit[,step] do ... end`, `while ... do ... end`, `break`, one-name `local`, `return`, one-target/one-value assignment, and calls. Semicolons are accepted/skipped as empty separators. Not a generic-for parser, standalone-do parser, named-function-statement parser, or multi-local/multi-assignment parser. Sources: `machine/bios/compiler/parser.lua:347-407,427-550`.
- Local syntax is `local name [<const>] [= expression]`, with exactly the `const` local attribute; any other identifier in `<...>` raises `unsupported local attribute '<name>'` at its position. Sources: `machine/bios/compiler/parser.lua:374-407`.
- Functions are only anonymous `function(name,...) ... end` with ordinary identifier parameters. No vararg token/node: `...` lexes as separate dots and fails where a parameter identifier/expression is expected. Source: `machine/bios/compiler/parser.lua:552-582`; token punctuation: `machine/bios/compiler/token.lua:1-48,74-97`. `local function name` fails at expected identifier because local requires the name next; `function name` fails at expected `(`. Sources: `machine/bios/compiler/parser.lua:377-379,555-556`.
- Return accepts zero or more comma-separated expressions; top-level input is parsed as an ordinary block then EOF (not a function-declaration-only form). Sources: `machine/bios/compiler/parser.lua:79-89,409-425,584-597`.
- Lexer/parser diagnostics use `[load:<chunk_name>] <message> at <line>:<column>`. Parser `expect` uses `expected '<token name>'`; unsupported primaries use `unsupported expression`, and a non-assignment/non-call expression statement uses `expected assignment or function call`. Sources: `machine/bios/compiler/lexer.lua:76-80`; `machine/bios/compiler/parser.lua:7-29,185-190,366-371`.

## Semantic acceptance: established

- Chunk body is rebound as a synthetic zero-parameter root function, so executable statements and top-level return are ordinary body semantics. Sources: `machine/bios/compiler/semantic.lua:409-435`.
- Return must be the final non-semicolon statement of its immediate block. Before binding that statement or its expressions, binder raises `return must be the final block statement` if another statement follows. Sources: `machine/bios/compiler/parser.lua:535-543`; `machine/bios/compiler/semantic.lua:374-384`.
- `break` binds only with positive loop depth; nested functions reset loop depth to zero. Error `break outside loop`. Sources: `machine/bios/compiler/semantic.lua:325-346,365-368,387-405`.
- `const` without initializer raises `const local '<name>' needs an initializer`; assignment to a const direct name (local/upvalue/external binding) raises `cannot assign to const local '<name>'` before RHS binding. Member/index writes through a const name are not blocked by this check. Sources: `machine/bios/compiler/semantic.lua:267-305`.
- Local initializer binds before the new local is introduced. Duplicate same-function parameter names raise `duplicate function parameter '<name>'`. Block scopes restore previous same-name local bindings. Sources: `machine/bios/compiler/semantic.lua:44-60,68-107,290-305,374-405`.
- Name resolution: active local, parameter, recursively captured enclosing local/parameter (upvalue), supplied external name, then selected environment/global key. The capture chain preserves the actual binding; child functions inherit environment/external-name configuration. Sources: `machine/bios/compiler/semantic.lua:109-195,387-402`.
- If an external entry exists, `is_type` raises `Struct type '<name>' is not a runtime value.` before checking `available`; unavailable raises `no live location for '<name>'`. An absent external entry is not an unknown-name error for source-string names; it proceeds to environment/global access. Sources: `machine/bios/compiler/semantic.lua:168-187`.
- Semantic member/index paths must recursively start at a visible name: literal/call/function-result member/index access can parse but fails `paths must start at a visible binding`. This path restriction is distinct from method-call receivers: `f():method()` is a call node rather than `f().field` member path. Bind assignment validates its path before RHS. Sources: `machine/bios/compiler/semantic.lua:197-218,220-249,267-287`; `machine/bios/compiler/parser.lua:216-241`.

## Lowering, results, and scope use: established

- All ordinary grammar statement kinds have code-generation dispatch: assignment, call statement, local, if, while, numeric-for, break, return. Function expressions have closure-address emission, not interpreted function text. Sources: `machine/bios/compiler/compiler.lua:851-857,1613-1647`.
- Bare `return` lowers to **one nil result**; falling through an empty/non-return-final function body also adds a **one-nil** return. This is not a claim of stock Lua zero-result behavior. Sources: `machine/bios/compiler/compiler.lua:1133-1146,1738-1744`.
- Each ordinary call used as a value requests one result. The last unparenthesized call in an argument list expands its physical result tuple into arguments, and the last unparenthesized call in a return list forwards its tuple after preceding return values. Parenthesized call is nonexpanding. Sources: `machine/bios/compiler/parser.lua:177-183,233-238`; `machine/bios/compiler/compiler.lua:648-684,859-867,1151-1185`.
- Method call evaluates receiver once into the `self` argument register and fetches method by its name, then evaluates explicit arguments in order. Ordinary call evaluates callee before its arguments. Sources: `machine/bios/compiler/compiler.lua:604-675`.
- Uninitialized non-const local emits nil; initialized local emits one value. Numeric-for evaluates start, limit, optional step into locals and defaults omitted step to 1. Sources: `machine/bios/compiler/compiler.lua:1102-1121,1420-1482`.
- Unknown ordinary source names without an environment compile through captured `__bmsx_getglobal` / `__bmsx_setglobal` primitives. Explicit-environment name accesses use table get/set operations. External bindings call the supplied scope's `read`/`write` accessor with the external descriptor. Sources: `machine/bios/compiler/compiler.lua:8-12,76-97,407-442,956-1011`. Binder precedence (local/parameter/upvalue before external before env/global) is listed above; source `_env`/other names are not special in that binder.
- Compile first calls semantic binding for the whole chunk, then prepares/compiles the root and collected child functions. Register-limit check occurs after each function emission and raises `[load:<chunk_name>] function or expression needs too many registers` (no appended source position there). Source: `machine/bios/compiler/compiler.lua:1881-1903,1936-1945`. Allocation/encoding limits are other packet's scope.

## Exact parser/lowering mismatch: stop at this boundary, not a language guarantee

- Unary `&` is accepted with any unary operand by `machine/bios/compiler/parser.lua:246-269`. `machine/bios/compiler/semantic.lua:251-261` folds only `&` applied directly to a string-literal node (parentheses around that literal preserve node identity); other operands are bound as normal runtime expressions. But `machine/bios/compiler/compiler.lua:33-37` contains no opcode mapping for `syntax.unary_string_id`, while `machine/bios/compiler/compiler.lua:869-883` indexes that map for nonconstant unary nodes. Therefore this sheet establishes literal `&"text"` support only; it does **not** assert dynamic `&expr` successfully lowers or state an exact public error for it. Owners disagree here; no runtime/compiler repair or speculative fallback has been attempted.

## Linked-source parser contrast: not the installed runtime grammar

The following confirms **linked/tooling parser forms**, not a comprehensive linker/compiler-acceptance audit. Runtime behavior above is read from the BIOS parser itself; do not route source through the tooling parser/linter and assume `load` will accept it.

- Tooling parser consumes initial `module<const>` / `module<entry>` and sets chunk flags: `toolchain/ts/lua/syntax/parser.ts:182-198,246-264`. Runtime begins with ordinary `parse_block` and has no such directive prepass: `machine/bios/compiler/parser.lua:584-597`. These words are ordinary runtime identifiers/comparison tokens, not module directives.
- Tooling parser recognizes `struct`, `bss name:type`, `data name:type = expression`, and `rodata name:type = expression`; type refs can contain array brackets. Sources: `toolchain/ts/lua/syntax/parser.ts:437-543,1429-1442`. Runtime statement dispatch/local grammar has no declaration/type-reference branch: `machine/bios/compiler/parser.lua:374-407,513-533`; thus these declaration forms are not runtime declarations.
- Tooling locals accept a `:*type` pointer annotation, multiple names/values, local-function declarations, and `<init>` on a local function. Sources: `toolchain/ts/lua/syntax/parser.ts:545-579,613-674`. Runtime local grammar accepts one name with only `<const>`, with no pointer annotation or local-function branch: `machine/bios/compiler/parser.lua:374-407`; runtime anonymous function grammar consumes `(` immediately after `function`: `machine/bios/compiler/parser.lua:552-582`.
- Tooling parser has named-function, repeat, standalone-do, goto, halt-until-IRQ branches and vararg/table-constructor primary forms. Sources: `toolchain/ts/lua/syntax/parser.ts:409-433,1339-1344`. Runtime statement/primary dispatch and token table do not provide these as equivalent forms: `machine/bios/compiler/parser.lua:124-191,513-533`; `machine/bios/compiler/token.lua:1-48,50-72`. For example runtime `{` cannot tokenize (`unexpected character`), `...` is dots rather than a vararg expression, and `function name` fails expected `(`. A name such as `repeat` not in runtime keyword table can still be used as an ordinary identifier; absence of a language keyword is not a ban on the spelling.
- A runtime load containing e.g. `local sum = function(a,b) return a+b end; return sum(2,3)` follows runtime source shapes. Recursive local use must account for initializer-before-binding: `local f = function() return f() end` does not make that inner `f` resolve to the new local; a preceding `local f; f = function() ... end` can capture the already-visible local. Sources: `machine/bios/compiler/parser.lua:374-407,552-582`; `machine/bios/compiler/semantic.lua:128-168,290-305`.

## Lexer current-token shape and phase separation

- The BIOS lexer exposes **one mutable state** returned by `lexer.new`, not a persistent token-object list. State has `source`, `chunk_name`, `index`, `length`, `current_code`, `line`, `column`, `token_kind`, `token_line`, `token_column`; lexer writes `token_lexeme` for identifiers/keywords and `token_literal` for number/string tokens. `next` updates only applicable payloads, so unrelated payload fields must not be interpreted for a different `token_kind`. Sources: `machine/bios/compiler/lexer.lua:287-342`.
- Token kinds are numeric private compiler-token constants. Parser consumes them using `match`/`expect`/`consume_identifier`, constructs AST nodes using separate `syntax` numeric tags, and translates token operators to AST operators. It does not carry lexer token state into chunk AST. Sources: `machine/bios/compiler/token.lua:1-48`; `machine/bios/compiler/syntax.lua:1-43`; `machine/bios/compiler/parser.lua:12-54,91-122,584-597`. Exact factory AST/list shape is syntax agent's packet, not a token-list contract.
- Parser errors precede semantic/compiler errors because the source path parses a complete chunk before semantic compile; compiler starts with semantic binding. Source parser entry: `machine/bios/compiler/parser.lua:584-597`; compiler entry: `machine/bios/compiler/compiler.lua:1881-1887`; public orchestration is root's API packet. Within semantic binding, statement order is source order and expression paths/callee/operands are bound in explicit traversal order, not a separate typechecking pass. Sources: `machine/bios/compiler/semantic.lua:197-264,267-311,374-384`.

## Lexical literals: bounded additional facts

- Numeric scanner accepts decimal digits with a fractional dot only when followed by a digit, optional `e`/`E` exponent with optional sign and required digits, leading-dot decimals when next character is digit, and `0x`/`0X` hexadecimal integers. It delegates scanned text to `tonumber`. Errors are `invalid numeric literal exponent`, `hexadecimal literal requires digits`. Sources: `machine/bios/compiler/lexer.lua:124-181,327-336`. No claim is made about numeric range/rounding here; primitive/numeric owners are outside this extraction.
- Strings require single/double quotes. Literal CR/LF or end before closing quote raises `unfinished string`. Escapes: quotes/backslash, `a b f n r t v`, up to three decimal digits (<=255), exactly two hex digits after `x`, and `z` followed by skipped whitespace. Errors: `decimal escape too large`, `invalid hexadecimal escape`, `invalid escape sequence`. Sources: `machine/bios/compiler/lexer.lua:183-265,338-342`. No long-string scanner is present in token/primary/string branches (`machine/bios/compiler/token.lua:1-48,74-97`; `machine/bios/compiler/parser.lua:124-191`).
