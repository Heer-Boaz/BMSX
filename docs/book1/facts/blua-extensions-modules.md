# BLua module / static-import / startup source facts

Scope: read-only source inventory at HEAD `d5f491bd3`. Facts below come from the source paths cited, not documentation. No builds/tests were run and no source was edited. This is a bounded, partial packet, not a prose chapter or full BIOS/loader audit.

## Source forms and compile-time namespaces

- **Parse-time module markers:** `module<const>` or `module<entry>` is recognized only at the beginning of a chunk, before its block is parsed. Optional `;` follows the marker. The marker names are matched case-sensitively (`const`, `entry`), and the parser stores separate `constModule` / `entryModule` flags. This inspected parser does not itself establish entry-selection policy. Source: `toolchain/ts/lua/syntax/parser.ts:182-198,246-264`.
- **Explicit module export site:** the recognized export is exactly the chunk's last top-level statement when that is `return` with exactly one expression. Earlier/nested returns are not the declared export site. Source: `toolchain/ts/lua/semantic/module_bindings.ts:22-27`.
- **Ordinary module root versus const namespace:** compile context gives a non-const module with a recognized export a single root export slot (`''`). Const modules additionally get statically shaped named export paths and compile-time leaf values / function symbols. Source: `toolchain/ts/lua/compiler/passes/module_contract.ts:96-150`.
- **Const namespace export leaves:** recognized values include nil, booleans, numbers, strings, storage-address symbols (`bss`, `data`, `rodata`), and supplied link values. The literal evaluator handles literal nodes, bound earlier single-name/single-value top-level `local name <const> = ...` values, unary numeric negation, and numeric binary expressions supported by the shared compile-time numeric evaluator. This is not a claim that every expression is a compile-time constant. Sources: `toolchain/ts/lua/compiler/passes/const_module_exports.ts:30-111,114-137`; `toolchain/ts/lua/compiler/passes/module_contract.ts:120-138`.
- **Const-export restriction:** each statically shaped leaf must have a compile-time constant value or static function symbol, else compilation throws `Const module '...' export '...' is not a compile-time constant or static symbol.` Named table shape is built by inspecting named fields and top-level local table/assignment/function-declaration shapes. Sources: `toolchain/ts/lua/compiler/passes/const_module_exports.ts:140-185`; `toolchain/ts/lua/compiler/passes/module_shape.ts:50-65,93-175`.
- **Const modules do not imply a runtime immutable table:** accepted const-module compile info causes the ordinary module runtime proto to be omitted; exports are compile-time symbols/inlined values. Such modules are also skipped when marking static runtime initialization paths. Sources: `toolchain/ts/lua/compiler.ts:2375-2395,6331-6337`.
- **`local name <const>` is not `module<const>`:** a current-function const local owns an immutable register, and a read uses that resident register. Imported namespace/function bindings instead can be compiler-only path/call-target bindings. Const-member snapshots and mutable module aliases still use ordinary cells; a captured const ordinary-module root is read through the module's published root storage. Sources: `toolchain/ts/lua/compiler.ts:2588-2601,2671-2682,2745-2811`. Exact general assignment/const grammar beyond the inspected forms was not inventoried.

## Literal imports and static BIOS function targets

- **Require form at the compiler boundary:** unshadowed identifier `require` must have exactly one literal string module path and no method component, else compilation throws `Compile-time require expects exactly one literal module path.` A lexical `require` binding is not treated as this builtin. Missing source/installed contract throws `Compile-time require module '...' was not provided to the program compiler.` Source: `toolchain/ts/lua/compiler.ts:2398-2445`.
- **Dependency inclusion:** dependency collection finds syntactic non-method calls named `require` with exactly one literal string argument, normalizes paths, and deduplicates known module paths. Closure construction visits those dependencies recursively. The selected executable consists of entry dependencies plus explicitly supplied module roots and their dependencies, not every workspace module. Source: `toolchain/ts/lua/compiler/module_graph.ts:11-59,62-80`. This syntactic discovery pass itself does not inspect lexical shadowing (contrast the compiler resolver immediately above).
- **Path spelling:** `toLuaModulePath` removes `.lua` case-insensitively, turns backslashes into slashes, strips `carts/<cart>/` or `machine/bios/res/`, `machine/bios/`, `res/` prefixes. It does not convert dots to directory separators. Source: `toolchain/ts/lua/module_path.ts:1-33`.
- **Static path forms:** the compiler resolves import roots, identifiers bound to imported paths, `.member`, and `["literalMember"]` into an exported path. Dynamic index expressions are not static path components. Source: `toolchain/ts/lua/compiler.ts:2466-2525`.
- **Named BIOS imports are installed compiler contracts:** cart compilation records supplied BIOS function descriptors by `(path, exportPathKey)` and rejects a BIOS import whose module path conflicts with a provided source module. A resolved installed import path yields a `bios_function` call target by import index. Sources: `toolchain/ts/lua/compiler.ts:968-978,2557-2584,6216-6226`. The actual BIOS descriptor producer, its public names/signatures, installation and physical-address relocation were NOT inspected, so this packet cannot assert a callable public BIOS list or exact final runtime call encoding.
- **Useful resolved shapes (not executed examples):** `require("path").named(...)`, a static `["named"]` selection, or a const local naming the namespace/function path are resolved through the above import/path ownership. `resolveConstLocalModuleBinding` recognizes static call targets and const namespaces without leaf values as compile-time local bindings. Sources: `toolchain/ts/lua/compiler.ts:2466-2525,2588-2601,2671-2682`. Local-declaration lowering and complete call lowering were not inspected; parent should verify exact example syntax against its selected BIOS export before presenting a complete hardware example.
- **Static targets are not function values:** attempting to load a resolved source static function export or installed BIOS function import as a Lua runtime value fails `Static function export '...' is a call target, not a Lua runtime value.` Compiler-only module/namespace roots fail runtime-value use with `Module '...' root is compile-time only; access an exported field instead of using the module table as a runtime value.` A const value export used as a call target fails `Const module '...' value export '...' is not a call target.` Sources: `toolchain/ts/lua/compiler.ts:2664-2695,2741-2758,2791-2797`; member/index lowering rejection sites found at `toolchain/ts/lua/compiler.ts:4782-4784,4822-4824`.

## Exported static function restrictions

- **Source static function forms:** const-module return trees can name a function literal directly (including root `return function(...) ... end`), or a bound top-level `local function name(...) ... end`, or top-level `local name <const> = function(...) ... end`. Named table fields recurse to named exported functions. A root function has the empty export path; named functions have their export path. Multiple export names for the same declaration are grouped into one static function body with multiple slots. Source: `toolchain/ts/lua/compiler/passes/static_functions.ts:38-120,124-148`.
- **No captured runtime local:** after compiling an exported const-module function, any upvalue causes compilation failure; the diagnostic permits compile-time constants, parameters, function-local declarations, static calls, and static storage. Source: `toolchain/ts/lua/compiler.ts:6251-6284`.
- **Instruction-level static lane:** exported functions are checked for forbidden runtime-global slot access, table allocation/dispatch, Lua object length, runtime closure allocation, vararg dispatch, dynamic string concatenation, and ordinary string `LOADK`. Numeric/boolean constants, scalar locals, static calls, branches, memory loads/stores are the stated allowed lane. `LOADKR` of already interned typed `.rodata` constants is explicitly permitted; symbolic relocated `LOADK` also bypasses the ordinary-string check. Source: `toolchain/ts/lua/compiler/passes/static_proto_contract.ts:6-63`. This is emitted-instruction validation, not a complete source grammar blacklist.

## Fresh startup and `<init>` consequences

- **Marker syntax and placement:** parser accepts `local function name <init>() ... end`; function attribute names are lowercased, and names other than `init` are unsupported. Placement validation requires module/chunk-top-level local functions, zero parameters, no varargs, and rejects `<init>` in a compile-time module. Sources: `toolchain/ts/lua/syntax/parser.ts:545-579`; `toolchain/ts/lua/compiler/passes/init_participants.ts:23-65,82-115`.
- **Participant ordering:** participants are recorded per module. A module declaring one must be the entry or a statically required module, else compilation fails. The init-vector order is dependency/static-module order, then entry participants. Source: `toolchain/ts/lua/compiler.ts:896-937`.
- **Critical fresh-start distinction:** generated *normal startup* calls generated section initialization, then static ordinary-module initializers, then the entry proto. It does **not** call the generated init-vector or individually invoke `<init>` participants. Sources: `toolchain/ts/lua/compiler.ts:1561-1588,6393-6402`. Thus do not teach `<init>` as an automatic one-time constructor on ordinary startup based on the marker alone. The source inspected here does not establish how a normal author explicitly invokes its marked function (local-function declaration lowering was not inspected).
- **Separate generated init-vector:** when participants/static modules exist, a separate proto is generated. Its body first ensures static module initializers and then loads and calls each registered participant with zero arguments. Sources: `toolchain/ts/lua/compiler.ts:1592-1610,6382-6391`. Which non-startup consumers invoke this vector is intentionally uninspected in this bounded packet.
- **Generated storage init:** section initialization copies `.data` words from image/LMA address to live/VMA address, then zeros `.bss` words, then returns. The code emits direct machine memory word loads/stores. Source: `toolchain/ts/lua/compiler.ts:1505-1558`. Exact region addresses/layout and reset/cart-install lifetime owners are outside this packet.
- **Ordinary-module initialization:** compile-time static path marking descends dependencies before recording a module and rejects cycles with `Compile-time require cycle includes module '...'`. Emitted initializers read a separate module-initialized slot, skip an already true one, call the module proto, then publish true only after return; this state is independent of the returned export (including nil/false). Sources: `toolchain/ts/lua/compiler.ts:2375-2395,1613-1630`; `toolchain/ts/lua/module_path.ts:38-39`.
- **Partial system/cart boundary facts only:** participant storage uses system global slots when `programDomain === 'system'`, ordinary global slots otherwise. Cart compilation may install BIOS function contracts; system compilation marks all provided ordinary modules for static initialization and normal system startup clears boot primitives before entry. Sources: `toolchain/ts/lua/compiler.ts:896-906,6216-6226,6377-6380,1572-1583`. Do not generalize this into a complete lifetime claim: actual BIOS installation, system reset versus cart reload, module export publication and linker/storage address ownership were not inspected.
