# BLua extension spellings: finite supplemental facts

2026-10-18, HEAD866396a64 (priority-only change since d5f491bd3). Read-only actual parser/compiler inspection. No runtime edits; no architecture/PDF input. No comprehensive Lua comparison.

- O01: Augmented assignment spellings are exactly `+= -= *= /= %= ^=` in addition to ordinary `=`. Assignment requires exactly one target and one RHS for an augmented operator. Source: toolchain/ts/lua/syntax/parser.ts:927-952,977-1007.
- O02: Targets are prepared first; RHS compiled second; then compound arithmetic reads target and writes result. The compiler supports local, upvalue, global, table, cop0 and memory targets. Source: toolchain/ts/lua/compiler.ts:4025-4039,4237-4288. Mapped/CP0 consequences are in sibling intrinsics packet. Do not describe as textual replacement or atomic operation.
- O03: Unary `&` first tries to resolve a typed storage selection and emits that selection's address without reading it. Source: toolchain/ts/lua/compiler.ts:5248-5252.
- O04: Otherwise linked compiler permits statically classified string/string_id/unknown, rejects other classified kinds, then compiles operand unchanged for one result. This use retains a String, not an exposed numeric string-ID or byte pointer. Unknown classification does not establish universal runtime type validation. Source: toolchain/ts/lua/compiler.ts:5254-5276.
- O05: Compile-time StringId unary evaluation retains the string expression unchanged. Source: toolchain/ts/lua/compiler.ts:3355-3356.
- O06: Parser recognizes `base->member` alongside `base.member`, retaining member operator Arrow vs Dot on a MemberExpression. Source: toolchain/ts/lua/syntax/parser.ts:1136-1138,1154-1159,1189-1196.
- O07: Member value lowering uses cop0, static export or typed scalar address resolution before ordinary Table selection and does not switch on arrow vs dot. Therefore arrow is another named-member spelling here, not C's automatic extra pointer load. Source: toolchain/ts/lua/compiler.ts:4768-4794.
- O08: The typed-field resolver uses expression.base's typed address then field offset, not reading an addr field into a new typed pointer. Source: toolchain/ts/lua/compiler.ts:5089-5095.
- O09: An identifier begins ASCII lowercase a-z,_,$; following characters additionally permit decimaldigits. Any uppercase ASCII in identifier is explicitly rejected, and other letters are not accepted by the character predicates. Source: toolchain/ts/lua/syntax/lexer.ts:263-284,612-629. This is a relevant BLua source convention, not itself a claim of new functionality.
- O10: A binary multiplication `*` at a new line stops the current expression, permitting a new dereference statement. No universal line-break rule for all operators is established. Source: toolchain/ts/lua/syntax/parser.ts:1107-1117.
- O11: Local `<const>` is shared with the explicit Lua5.4 reference, not solely a BLua invention. Official primary reference: https://www.lua.org/manual/5.4/manual.html#3.3.7 (local attributes const/close). Production reference actually inspected: https://github.com/lua/lua/blob/v5.4.8/lparser.c, getlocalattribute/localstat1599-1660. This reference does NOT supply BLua facts or future-version compatibility. General language pointer is https://www.lua.org/docs.html; no general tutorial/standard-library catalogue is requested.
