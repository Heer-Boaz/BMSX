# GPU shared-VRAM / buffer-lifetime facts

Extraction only. Live checkout inspected at HEAD `77216358a`. No repository edits, suites, architecture document, reference PDF, runtime, BIOS, or cart changes. Scope: paired GPU/spec/command-buffer/local-memory/device-output owners; narrowly paired software consumer for actual memory use. Root separately owns other-backend and DMA corroboration.

**GV01 — RAW: address representation.** GX VRAM addressing has a 1024-word X period, 1024-row Y address period, two bytes per address word; the Y extension chooses a 511 or 1023 mask. Local-memory format address functions return masked word addresses, not resource handles or allocation IDs. This describes the address lattice, NOT installed allocation size or private texture/framebuffer partitions.
- `machine/ts/spec/gx/vram.ts:1-13`; `machine/cpp/spec/gx/vram.h:9-21`.
- `machine/ts/machine/devices/gx/gpu_local_memory.ts:12-33,45-100`; `machine/cpp/machine/devices/gx/gpu_local_memory.h:18-34,48-84`.

**GV02 — RAW: GPU receives/copies words, not a DMA RAM-source reference.** CPU GP0 writes pass a raw word to the command FIFO. DMA GP0 writes copy words into the separate ingress FIFO; GPU processing is deferred until `MAPPED_BUS_DMA_BLOCK_END`. The GPU entrypoint receives `(word,busSignals)`, not a source RAM address. Both FIFO capacities are 16 words. This boundary alone does NOT prove when DMA has read each source RAM word.
- `machine/ts/machine/devices/gx/gpu.ts:1034-1074,1135-1144`; `machine/cpp/machine/devices/gx/gpu.cpp:551-590,653-662`.
- `machine/ts/spec/gx/gp0.ts:27,33-42`; `machine/cpp/spec/gx/gp0.h:34-44`.

**GV03 — RAW: queued command capture is packet words plus raw context words, NOT texture/CLUT bytes.** FIFO parsing copies packet words into the fixed packet buffer; emission copies those words into owned command-buffer storage. The queued descriptor records kind/opcode, packet offsets/count, draw mode, Y extension, texture window, drawing area/offset, mask mode, skipped-line parity. It has no texture/CLUT byte snapshot, RAM-source pointer, private framebuffer copy, or buffer-ownership tag. Texture coordinates/attributes remain packet words.
- `machine/ts/machine/devices/gx/gpu.ts:1183-1190,1765-1784`; `machine/cpp/machine/devices/gx/gpu.cpp:751-758,1248-1266`.
- `machine/ts/machine/devices/gx/gpu_command_buffer.ts:223-236,396-407,418-445`; `machine/cpp/machine/devices/gx/gpu_command_buffer.h:208-220,380-390,401-427`.

**GV04 — RAW: upload payload lifetime changes at word ingestion.** CPU-to-VRAM header words and then payload words are copied into command storage. The normal upload command is pushed only when its expected payload-word count reaches zero; expected words are `(width*height+1)>>1`. The queued upload therefore uses retained payload words, not a later read through an original CPU/DMA RAM-source address. Destination XY/size remain packet words until consumer execution.
- `machine/ts/machine/devices/gx/gpu.ts:1652-1660,1675-1681,1805-1812`; `machine/cpp/machine/devices/gx/gpu.cpp:1130-1137,1152-1158,1285-1292`.
- Narrow actual consumer: `machine/ts/render/backend/software/gx_gpu_commands.ts:75-98`; `machine/cpp/render/backend/software/gx_gpu_commands.cpp:40-75`.

**GV05 — RAW, software consumer: texture and CLUT are live shared-VRAM accesses when the retained draw executes.** Texture sampling reads `software.vram` at page/UV-derived coordinates; indexed modes fetch their CLUT word from the same `software.vram`. Destination write helpers read the current destination word for mask testing/blending and then write that same VRAM storage. Queue-time raw context capture in GV03 is not texture-content capture.
- `machine/ts/render/backend/software/gx_gpu_rasterizer.ts:112-139,435-447`; `machine/cpp/render/backend/software/gx_gpu_rasterizer.cpp:65-90,481-492`.
- `machine/ts/render/backend/software/gx_gpu_vram.ts:38-44,115-126`; `machine/cpp/render/backend/software/gx_gpu_vram.h:50-61,106-123`.
- **Derived caution:** contents needed by an earlier draw must be preserved in that draw's ordered execution history. This is NOT a claim that a later, correctly ordered GP0 upload requires waiting for host presentation, nor that host access is fenced by guest status.

**GV06 — RAW, software consumer: command order and VRAM-copy source.** The consumer visits retained command indices in increasing order up to its command limit. VRAM-to-VRAM copy decodes source/destination coordinates from packet words, reads source words from its current VRAM, then writes destination words there; it does not snapshot copy-source bytes when the GPU queues the packet. Horizontal overlap selects forward/backward column order; rows advance forward.
- `machine/ts/render/backend/software/gx_gpu_commands.ts:102-137,276-302`; `machine/cpp/render/backend/software/gx_gpu_commands.cpp:78-136,289-319`.
- **Derived caution:** same-storage texture/CLUT/destination overlap is representable behavior, not an automatic allocation error or an automatic private copy. Do not replace the exact consumer traversal with an invented universal overlap/atomicity rule.

**GV07 — RAW: guest execution timing is separate from backend retirement/publication.** The GPU processes the next FIFO command only with no pending command deadline and an IDLE readback port. Deadline completion advances `executedCommandCount` and resumes processing; it does not itself run a rasterizer or publish a display. GPUSTAT IDLE requires empty ingress/FIFO, no partial packet/upload/polyline, no pending timing, and readback IDLE; it does NOT require `commandCount == 0`, retirement, a presentation event, or a published VRAM snapshot.
- `machine/ts/machine/devices/gx/gpu.ts:1153-1158,1264-1294,1905-1913`; `machine/cpp/machine/devices/gx/gpu.cpp:721-726,762-771,684-702,1382-1390`.
- `machine/ts/machine/devices/gx/gpu_command_buffer.ts:410-415`; `machine/cpp/machine/devices/gx/gpu_command_buffer.h:393-398`.

**GV08 — RAW: GP0 IRQ marker is in-order guest processing, not a host-render/display fence.** GP0 opcode `1f` raises the GPU interrupt request when reached by the sequential GP0 parser, then starts its one-tick command timing; no raster command is appended for it. GP1 acknowledge clears the interrupt-request bit. Neither path retires commands or latches presentation.
- `machine/ts/spec/gx/gp0.ts:7`; `machine/cpp/spec/gx/gp0.h:14`.
- `machine/ts/machine/devices/gx/gpu.ts:1204-1211,1355-1358`; `machine/cpp/machine/devices/gx/gpu.cpp:784-790,864-867`.
- **Derived caution:** distinguish guest ordered-work completion from actual backend bytes/display publication. The marker's request bit is level-retained until acknowledged, not a per-buffer lifetime object.

**GV09 — RAW: readback source/fence admission and completion phases.** A retained VRAM-to-CPU command activates readback only when command execution reaches it. Activation captures decoded XY/size, the command's Y extension, a prefix fence count, resets the cursor, increments a token, and enters PENDING. A backend may claim only PENDING at the exact fence count, entering SUBMITTED; completion reaches READY only while still SUBMITTED with the same token. GP0 parsing remains blocked while readback is not IDLE.
- `machine/ts/machine/devices/gx/gpu_command_buffer.ts:119-159,205-208,410-415`; `machine/cpp/machine/devices/gx/gpu_command_buffer.h:88-100,131-141,185-187,393-398`.
- `machine/ts/machine/devices/gx/gpu.ts:1153-1156`; `machine/cpp/machine/devices/gx/gpu.cpp:721-724`.

**GV10 — RAW, software consumer: readback bytes are copied into the owned readback buffer before READY.** Consumer execution first brings retained commands through the requested prefix, then copies source VRAM words to `readback.pixelBytes`, then completes its token. GP0 reads consume those retained bytes in pairs of 16-bit pixels, with an unpaired final pixel left in the low half of the word; final consumption returns readback to IDLE and clears geometry/cursor. This is not direct GPU writing of CPU RAM; DMA RAM destination ownership lies downstream of GP0 word consumption.
- `machine/ts/render/backend/software/gx_gpu.ts:18-45`; `machine/cpp/render/backend/software/gx_gpu.cpp:26-64`.
- `machine/ts/machine/devices/gx/gpu_command_buffer.ts:163-184`; `machine/cpp/machine/devices/gx/gpu_command_buffer.h:107-128`.

**GV11 — RAW: CPU/DMA GP0-port ownership and capacity safeguards.** CPU GP0 reads advance READY readback only when DMA does not own the read port; otherwise the existing GPU-read latch is returned. CPU GP0 write-ready requires ingress empty, a physical FIFO slot, no DMA write-port ownership, and no supervisor ingress stop. DMA write-ready is a different condition; request lines depend on GP1 DMA direction and device readiness. These are word/port-flow safeguards, not texture/framebuffer region locks.
- `machine/ts/machine/devices/gx/gpu.ts:1019-1031,1878-1962,2025-2034`; `machine/cpp/machine/devices/gx/gpu.cpp:536-548,1356-1437,1499-1508`.
- `machine/ts/machine/devices/gx/gpu_command_buffer.ts:187-192`; `machine/cpp/machine/devices/gx/gpu_command_buffer.h:157-159`.

**GV12 — RAW: FIFO clear is not rollback or blanket cancellation of retained drawing.** GP1 FIFO clear FIRST discards DMA-ingress/FIFO words, THEN flushes only upload payload already consumed by the GP0 parser into command-buffer storage; it also clears partial packet/polyline state, runs the readback-abort transition, and completes an accepted raster/upload timing target still retained in the command buffer. A retained upload with >3 words is emitted with its actual retained word count; a header-only upload is removed. The software upload consumer emits only the pixels represented by the actual payload. Do not call this an all-or-nothing transfer or describe the surviving prefix as all port-admitted/accepted words. GP1 RESET/CLEAR and PCRTC CSR RESET/FLUSH all enter this same clear function (`machine/ts/machine/devices/gx/gpu.ts:1347-1353,1411-1419`; `machine/cpp/machine/devices/gx/gpu.cpp:856-862,920-928`).
- `machine/ts/machine/devices/gx/gpu.ts:1609-1627,1663-1672`; `machine/cpp/machine/devices/gx/gpu.cpp:1087-1105,1140-1149`.
- `machine/ts/render/backend/software/gx_gpu_commands.ts:84-96`; `machine/cpp/render/backend/software/gx_gpu_commands.cpp:52-72`.

**GV13 — RAW: readback abort branches and late-completion safeguard.** With readback IDLE, abort removes the next not-yet-executed C0 if present; otherwise it leaves retained commands alone. With PENDING readback, it truncates before that C0 and resets readback. For other non-IDLE phases it publishes a command-buffer revision and clears command/readback state. Resetting readback increments its token; a late completion cannot make that reset port READY because completion checks phase and token. No memory rollback is performed by these transitions.
- `machine/ts/machine/devices/gx/gpu_command_buffer.ts:134-159,210-215,248-275`; `machine/cpp/machine/devices/gx/gpu_command_buffer.h:96-100,144-154,190-195,228-255`.

**GV14 — RAW: full device reset differs from GP1/PCRTC reset.** Full `GxGpu.reset` resets command storage, initializes power-on VRAM bytes, publishes snapshot/replacement revisions, resets PCRTC/registers and ingress. GP1 RESET instead calls FIFO clear and register reset; it does not invoke power-on VRAM initialization. PCRTC CSR RESET additionally resets PCRTC and latches presentation registers; CSR FLUSH invokes FIFO clear. These facts do not cancel any independently owned DMA channel by implication.
- `machine/ts/machine/devices/gx/gpu.ts:475-499,755-772,1347-1354,1409-1421`; `machine/cpp/machine/devices/gx/gpu.cpp:66-90,285-302,856-863,918-930`.

**GV15 — RAW: actual owning presentation publication boundary.** `presentReadyFrameOnVblankEdge` synchronizes guest execution, latches PCRTC presentation words and GPU presentation registers, and seals `presentCommandCount`. Sealing chooses the readback fence count when readback is non-IDLE, otherwise the executed count. PCRTC latching copies register words into presentation words and publishes decoded scanout configuration. Device output uses these retained presentation words/registers. This proves a latched config plus command-prefix publication, NOT an atomic framebuffer-byte copy or per-pixel emulated VRAM-bus scanout.
- `machine/ts/machine/devices/gx/gpu.ts:746-752,1455-1467,1493-1514`; `machine/cpp/machine/devices/gx/gpu.cpp:276-282,960-972,975-996`.
- `machine/ts/machine/devices/gx/gpu_command_buffer.ts:384-389`; `machine/cpp/machine/devices/gx/gpu_command_buffer.h:368-373`.
- `machine/ts/machine/devices/gx/gpu_pcrtc.ts:723-730,825-826`; `machine/cpp/machine/devices/gx/gpu_pcrtc.cpp:446-453,548-549`.

**GV16 — RAW: output is an owner view; VRAM snapshot publication/retirement is explicit.** Device output retains the command buffer/readback port, PCRTC data, and GPU-owned VRAM snapshot storage. It is not a new immutable per-frame copy of texture/destination bytes. `commitRenderedVramSnapshotBytes` copies rendered bytes into GPU snapshot storage, publishes its revision, and retires the specified rendered prefix; ordinary prefix retirement shifts retained commands/words and rebases counts/fences. In the paired software path, presentation executes through `presentCommandCount` before scanout; explicit capture executes through `executedCommandCount` before committing bytes.

## Gaps / prohibited inference

- **DMADONE / addressed-RAM source or destination release:** not owned by GPU. Pair with root's DMA-owner facts, not GV02/GV10 alone. GPU timing IDLE and marker are separately scoped by GV07/GV08.
- **Other backends:** GPU queue shape proves no queue-time texture-byte snapshot. The live software VRAM traversal here is exact but backend-specific; root's separate narrow backend-prefix/scanout intersection sheet is needed for broader consumer claims. Do not generalize pixel-level self-overlap behavior from software to every backend without that precise evidence.
- **Faults:** no GPU fault register/transition was established in these leaves. Do not invent a fault-completion fence, rollback, payload zero-fill, or automatic region release. DMA fault behavior requires its owner.
- **Program discipline versus safeguards (DERIVED):** hardware owns word admission, timing/readback phases, port exclusion, token completion, decoded addressing and mask behavior. The captured command record contains no resource/buffer lifetime enforcement; planning non-destructive texture/CLUT/draw/display-region reuse is program ordering/region discipline, not an implicit texture copy or private framebuffer allocation.
- **Display visibility:** GV15 plus the actual prefix-to-scanout call proves the implemented publication contract. Neither GPU IDLE, GP0 marker, nor DMADONE alone proves a newly visible frame. No measured per-pixel bus timing, atomic double-buffer swap, host display completion, or direct host-VRAM-access guarantee is claimed.
- **Mirror check:** no true TS/C++ owner/spec mismatch found in the cited transitions. This is a bounded fact extraction, not an exhaustive renderer or whole-runtime parity audit.
