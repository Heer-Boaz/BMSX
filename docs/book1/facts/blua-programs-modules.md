# BLua32 cartridge source modules — finite verified fact sheet

Scope: source-program organization and compilation into a cartridge. Read-only extraction from current executable compiler, source parser, ROM builder/linker, paired CPU operations used by the lowering, and actual BIOS/SDK source examples. This is a fact sheet, not public chapter prose. No `docs/architecture.md`, reference PDF, IDE workspace solver, or test assertion was used as authority. No builds or runtime execution were performed by this extractor. There is one actual source compiler here, `toolchain/ts/lua/compiler.ts`; `compiler/program.ts` is program representation declarations, not a second compiler. The TS/C++ CPU owners listed below execute the emitted operations; do not invent a mirrored C++ source compiler. Existing Table/CPU7/BZ01 stops are not closed.

## Declaration, naming, and selecting a program

**M01.** An optional module attribute is parsed once, at the beginning of a chunk before its statement block. Recognized forms are `module<entry>` and `module<const>`; an optional semicolon may follow. A chunk without either is an ordinary source chunk. This syntax does not assign the module's name. The parser stores separate `entryModule` / `constModule` flags, with only the selected attribute true. Sources: `toolchain/ts/lua/syntax/parser.ts:182–198,246–264`.

**M02.** Normal ROM image construction calls entry resolution with no explicit override. Among admitted source modules, exactly one must have `module<entry>`: none produces “BLua program has no module<entry> root.”; more than one produces an error naming both roots. Source: `toolchain/ts/lua/entry_module.ts:7–31`; actual ROM caller: `toolchain/ts/rompack/blua32_image_builder.ts:134–146`. Limit: the general entry helper also has an explicit path override (`entry_module.ts:11–14`), but that is not used by this ROM caller; do not advertise a cartridge configuration override without another producer.

**M03.** The module path comes from the source path, not a Lua asset's numeric ID or the name of a local import variable. The source parser admits only Lua assets marked `program_module`, applies `toLuaModulePath(asset.source_path)`, and parses under that path. The path conversion changes backslashes to `/`, removes a final `.lua` extension case-insensitively, strips `carts/<cart-name>/`, or the first matching `machine/bios/res/`, `machine/bios/`, `res/` prefix. Other paths retain their text. Remaining path text is not lowercased and dots are not converted to slashes. Source: `toolchain/ts/rompack/blua32_image_builder.ts:84–106`; path owner: `toolchain/ts/lua/module_path.ts:1–32`. Source-derived examples: `carts/example/lib/settings.lua` → `lib/settings`; `cartlib/gx/display.lua` → `cartlib/gx/display`; `machine/bios/math/sin.lua` → `math/sin`. These examples apply the owner literally, not a file-search algorithm.

**M04.** The image builder rejects duplicate admitted module paths and generated-module conflicts with admitted paths. The compiler independently canonicalizes supplied module paths and rejects canonical duplicates. Sources: `toolchain/ts/rompack/blua32_image_builder.ts:134–144,168–185`; `toolchain/ts/lua/compiler.ts:5863–5877`. Do not present a duplicate-path winner, search-order fallback, or automatic namespace merging.

**M05.** The ROM program is selected from the entry plus explicitly supplied module roots, their transitive literal-require dependencies, and generated-module roots. System BIOS exports are additional roots in the system domain. A requested explicit module root missing from available modules is an error. Unreachable source assets need not become executable module functions. Sources: `toolchain/ts/rompack/blua32_image_builder.ts:203–222`; `toolchain/ts/lua/compiler/module_graph.ts:36–80`. Scope: this describes executable inclusion, not whether source text is retained as a debugging asset.

**M06.** Library inclusion follows the same literal-require closure over the product's available library paths. ROM builder produces a source-only/library distinction before `program_module` is set. Sources: `scripts/rompacker/rombuilder.ts:489–542,564–586,677–688`; transfer to asset word: same file `877–889`. Do not claim that `require` opens arbitrary filesystem files while a cartridge runs. Exact project-manifest include roots and asset schema are outside this extraction.

## Require expressions and initialization

**M07.** Built-in `require` is recognized only as an unshadowed identifier call. It requires exactly one string-literal module path and no method receiver; otherwise compilation reports “Compile-time require expects exactly one literal module path.” A lexical binding named `require` is not that built-in and follows ordinary call compilation instead. Source: `toolchain/ts/lua/compiler.ts:2418–2438`. Parser accepts both `require('lib/settings')` and string-argument sugar `require 'lib/settings'` as the same one-string-argument call shape: `toolchain/ts/lua/syntax/parser.ts:1231–1261,1291–1298,1303–1314`. Do not teach an alias of built-in `require`, computed path, extra search argument, or `package.path` search.

**M08.** The resolver first checks exact supplied names and their canonical path conversion, then installed module contracts; otherwise compilation reports “Compile-time require module '<name>' was not provided to the program compiler.” Source: `toolchain/ts/lua/compiler.ts:2398–2415`. This is a build-time error, not a runtime missing-file exception.

**M09.** The dependency collector recognizes identifier `require` calls with exactly one string-literal argument, canonicalizes the path, records only known source module paths, and deduplicates them in written traversal order. It walks nested expressions/functions, not only top-level assignments. Sources: `toolchain/ts/lua/compiler/module_graph.ts:11–33`; walker `toolchain/ts/lua/syntax/calls.ts:111–155` (function-expression body at150–152). Limit: dependency discovery is syntactic; do not promise perfect lexical-shadow filtering of the graph from M07's executable built-in recognition.

**M10.** Ordinary source-module initializers are scheduled during compilation. Recursive scheduling visits dependencies before recording the importer, deduplicates recorded module paths, skips recognized const modules, and rejects an ordinary dependency cycle with “Compile-time require cycle includes module '<path>'.” Sources: `toolchain/ts/lua/compiler.ts:2375–2395,884–894`. No runtime partial-module table is published to resolve such a cycle.

**M11.** Generated startup first calls section initialization, then the recorded ordinary module initializers, then the cartridge entry function. A require statement merely schedules ordinary modules (or emits nothing for installed / recognized const modules). A require expression on an ordinary module loads its retained export, not a new execution of the initializer at that source line. Sources: `toolchain/ts/lua/compiler.ts:1561–1584,5576–5589,5592–5623`. Thus an ordinary dependency's top-level work can already have happened before entry reaches its written `require`, including when the import was written inside a function. This is not stock Lua's first-evaluated-call loader contract. Do not promise a sibling initialization order based on a source filename, filesystem scan, or asset ID.

**M12.** Initializer completion uses a dedicated retained slot separate from the exported value. The generated loader reads this completion flag, skips if true, otherwise calls the initializer, then stores true only after successful return. A successful explicit `nil` or `false` export does not mean “not initialized” and does not trigger a second initializer call on a later require. Sources: `toolchain/ts/lua/module_path.ts:38–39`; emitted loader `toolchain/ts/lua/compiler.ts:1614–1629`. Physical slot operations execute in both owners: TS `machine/ts/machine/cpu/cpu.ts:2344–2357,2853–2857`; C++ `machine/cpp/machine/cpu/cpu_dispatch.inl:60–77,429–433`. These sources prove separate state and instruction semantics, not a reset/hot-reload lifetime policy; do not expand “once” beyond the initialized program state or claim host cache behavior.

## Ordinary exports

**M13.** Only the final top-level statement consisting of a `return` with exactly one expression declares a module export. Earlier/nested returns, a bare return, and final `return a, b` do not establish that export contract. Sources: `toolchain/ts/lua/semantic/module_bindings.ts:22–26`; executable contract consumer `toolchain/ts/lua/compiler/passes/module_contract.ts:102–106`. For ordinary code modules, the root is one runtime value and may be a table, function, scalar, false, or nil; the one expression is compiled as one result and stored as the export root. Source: `toolchain/ts/lua/compiler.ts:4372–4394`; ordinary root-slot production `toolchain/ts/lua/compiler/passes/module_contract.ts:139–151`.

**M14.** A recognized final export expression that is a function call, e.g. `return make_module()`, publishes only that call's first result. Extra results are not separate module exports. Source: `toolchain/ts/lua/compiler.ts:4382–4389` explicitly compiles the export expression with result count1, stores that one root and returns one value.

**M15.** A module without the final single-expression export contract is classified unshaped. Its require expression supplies `true`, followed by nil in additional requested result slots; it still has a scheduled initializer. A shaped ordinary require reads its root export slot and likewise supplies nil for extra result positions. Source: `toolchain/ts/lua/compiler.ts:2440–2456,5599–5622`. Limit: if a module has a declared final export but takes another early return without reaching that store, these facts do not justify claiming the early return becomes its exported value; avoid that pattern rather than inventing a fallback contract.

**M16.** Ordinary exported tables remain runtime values, not frozen const namespaces. Ordinary modules do not receive const-member export slots/static-function classifications: `toolchain/ts/lua/compiler/passes/module_contract.ts:109–122,139–141`. The compiler publishes/loads their root object via retained slots (`compiler.ts:2837–2844,4382–4389,5613–5622`) and ordinary field access compiles through the root and runtime table lookup (`compiler.ts:4768–4794`). Ordinary calls that are not static-module call targets compile their current callee expression (`compiler.ts:5637–5640,5661–5672`). Therefore two imports read the same published root, and replacement of an ordinary exported table field is observed through a subsequent ordinary `module.field()` lookup, rather than being permanently bound to the original function. Runtime field loads/stores: TS `machine/ts/machine/cpu/cpu.ts:2410–2449`; C++ `machine/cpp/machine/cpu/cpu_dispatch.inl:105–121`. This is not a claim that arbitrary optimizer/capture patterns are all audited; parent is separately executing a concrete ordinary-module program.

## Const modules and static imports

**M17.** `module<const>` is a compile-time export namespace for named static leaves or a root static function, not an ordinary runtime module table. The contract collects named export paths, compile-time constants/static-storage addresses, and static function symbols. Recognized const modules have no runtime initializer function and are not scheduled by ordinary require. Sources: `toolchain/ts/lua/compiler/passes/module_contract.ts:109–141`; `toolchain/ts/lua/compiler.ts:2382–2385,6331–6337`. Limit: the contract returns no shaped const-info if it finds neither a root static function nor a named export shape (`module_contract.ts:114–118`). Do not generalize that unsupported/malformed scalar-only `module<const>` returns are valid constant-module public APIs.

**M18.** Use `local settings<const> = require('lib/settings')` for a compile-time namespace, then access named fields; use `local operation<const> = require('a/static-function-module')` for a static call target and call `operation(...)`. Const local initialization records compile-time module bindings and can omit materialization of a runtime value. Sources: `toolchain/ts/lua/compiler.ts:2588–2601,2671–2681,3848–3855,3892–3905,4010–4012`. Member fields and literal-string indexed fields resolve through the same export-path mechanism (`compiler.ts:2504–2545,2607–2614`). Do not substitute a plain mutable local for the required compile-time alias without execution evidence.

**M19.** Recognized const leaf values include nil, boolean, number, string, and static BSS/DATA/RODATA addresses; generated link values are also a distinct producer-owned category. Numeric constant binary expressions and unary minus can be folded in these exports. Named table fields or literal string keys form the namespace tree; positional array fields and computed keys are not that named export mechanism. Sources: `toolchain/ts/lua/compiler/passes/const_module_exports.ts:30–42,44–111,114–159`; `toolchain/ts/lua/compiler/passes/expression_paths.ts:17–33`. A recognized named leaf that is neither a compile-time constant nor a static function symbol is an error (`const_module_exports.ts:163–185`). This list is not a promise that arbitrary runtime expressions, aliased mutable tables, or all language operators are constant-evaluable.

**M20.** A compile-time namespace root cannot be used as a runtime value: compiler error “Module '<path>' root is compile-time only; access an exported field instead of using the module table as a runtime value.” Static exported functions are call targets, not Lua runtime values; trying to materialize one reports that distinction. A const value export cannot itself be called. Sources: `toolchain/ts/lua/compiler.ts:2685–2690,2741–2757,5576–5611`. Do not store a static function import into a runtime table, pass it as an ordinary callback, return it as a runtime function value, or iterate a compile-time namespace as if it were an allocated table.

**M21.** Const function exports are compiled as scalar/static code and may not capture a runtime outer local. Their permitted emitted operations exclude runtime global reads/writes, table allocation/dispatch, object length, runtime closure creation, vararg dispatch, dynamic string concatenation, and ordinary Lua string constants. Dynamic call targets are rejected in this scope. Static typed memory/static-address operations and calls to other static exports are distinct from runtime table/object dispatch. Sources: `toolchain/ts/lua/compiler.ts:2942–2958,5644–5645,6257–6283`; actual opcode contract `toolchain/ts/lua/compiler/passes/static_proto_contract.ts:6–62`. Limitation: LOADKR of an already interned constant selected through immutable typed rodata is explicitly permitted (`static_proto_contract.ts:8–11`); do not turn the narrower ordinary string-constant prohibition into “no string value can ever occur.”

**M22.** `<init>` is forbidden in a const module. Elsewhere it must be a top-level local function, with zero formal parameters and no varargs. Placement validator errors are explicit. Source: `toolchain/ts/lua/compiler/passes/init_participants.ts:23–64`. This extraction does not establish all initial-participant invocation/reset semantics; omit those beyond this restriction rather than turning the attribute into an invented normal boot callback.

## Named BIOS function imports

**M23.** Current system public function exports are exactly root static functions at module paths `math/sin`, `string/float/decode`, `gpu/system_vram_region`. All have empty export-path key (the module root function). Source: `toolchain/ts/rompack/system.ts:9–22`. Actual matching producers declare `module<const>` and return a function: `machine/bios/math/sin.lua:1–2,38–46`; `machine/bios/string/float/decode.lua:1–8`; `machine/bios/gpu/system_vram_region.lua:1–11`. This is a finite system export list, not a claim that every BIOS file/module or global library table is independently importable by cartridge path.

**M24.** Cartridge compilation receives its named BIOS function contracts from the system import library; a supplied cartridge source module using the same path conflicts and is rejected. Installed named imports resolve to static BIOS call targets, not source-module initializers or Lua asset IDs. Sources: `toolchain/ts/rompack/blua32_image_builder.ts:213–231`; `toolchain/ts/lua/compiler.ts:6216–6225,2561–2583`. At link time the named import's function address becomes the function-call load relocation (`toolchain/ts/rompack/blua32_linker.ts:660–673`), and the system linker checks that each declared BIOS export really is a static function export (`same:524–548`). Do not teach a fixed BIOS function address as this API's identity.

**M25.** Actual BIOS/SDK use binds these imports with a const local and invokes that name as a function: `local sin_turn32<const> = require('math/sin')` then `sin_turn32(angle)`; `local decode_float<const> = require('string/float/decode')` then `decode_float(high, low, byte_count)`; `local system_vram_region<const> = require('gpu/system_vram_region')` then `local origin<const>, size<const> = system_vram_region()`. Sources: `machine/bios/math.lua:1,99–114`; `cartlib/bin.lua:1–4,117–120,133–136`; `cartlib/gx/vram.lua:1–2,100–104`. These are real named imports, not `control[...]` arrays or numeric asset IDs. Numeric meanings and complete routine contracts belong in canonical Math/String/Memory/device sections; this sheet admits the call style and written parameter ordering only.

## Limits / gaps for authors and reviewers

- No normative separate module-language spec leaf was found/read in this task. Direct parser/compiler/linker owners are authority for the facts above. No source/spec disagreement was observed because no competing normative module-language spec was provided; this is not a universal compiler-correctness claim.
- Exact lifecycle under whole-machine reset, execution-slot replacement, save/load, BIOS monitor restart, or live development is NOT established by M12. A narrow “one successful initialization in retained initialized program state” is proven; broader cache-lifetime claims require paired reset/execution owners.
- Exact recipe/project manifest root discovery, SDK installation, Lua asset retention and AEM/asset APIs were not extracted; root owns the concrete multi-module cart manifest/example and source can cross-link its verified route.
- No `package`, `package.loaded`, dynamic require search, implicit `.init`, dot-to-slash conversion, relative `./` or `..` normalization, source-order execution at each require call, circular partially initialized exports, or fallback table contract is supported by these facts. Omit rather than infer stock Lua behavior.
- No imported-module mutable global/environment lifetime, IRQ handler policy, class sugar, or all static-storage grammar is admitted beyond directly listed facts. These require separate facts / canonical cross-references.
- Actual output/assertion/runtime evidence for the new modules teaching cart is being collected separately by the root; do not present this read-only source extraction as a test run.
