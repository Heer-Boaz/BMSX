# Installed BLua32 program environment — finite facts

2026-10-18; current checkout inspected read-only. This sheet supplies environment/installation facts for a source-program chapter, not a complete library reference. The architecture document, reference PDFs and existing chapter prose were not consulted. Existing base facts were an index only. No build, execution, runtime repair or repository edit was performed.

## Installation and cartridge handoff

- ENV01. The system entry module requires `base`, then assigns ordinary public globals `table`, `string`, `coroutine`, `lua_compiler`, `load`, `os`, and `math`, in that order. `load` receives `lua_compiler.load`. Source: `machine/bios/main.lua:1–12`.
- ENV02. These assignments occur before system boot-screen initialization/the VBlank loop and before the cartridge handoff branch. That branch clears the terminal status, flushes, writes the IRQ mask to zero, then writes the selected startup address to `cop0.exec`. This is initialization before the normal cartridge-entry path, not a promise of a private fresh environment for every execution domain. Source: `machine/bios/main.lua:4–23,105–113,126–143`.
- ENV03. The paired EXEC datapaths reject a non-static/unreadable function record by hard-halt. The accepted path clears the call stack, selects the destination image, sets system/cartridge entry status and execution latches, then enters the static function with zero arguments. This accepted path does **not** call global-slot clearing; avoid describing EXEC as BIOS reinstallation, a global reset or a heap reset. Sources: `machine/ts/machine/cpu/cpu.ts:1523–1547`; `machine/cpp/machine/cpu/cpu.cpp:1095–1119`. Entry status constants: `machine/ts/spec/blua32/cop0.ts:6–14`; `machine/cpp/spec/blua32/cop0.h:12–20`.
- ENV04. A system reboot has a different route: reset-for-system-boot clears the execution environment, then CPU reset and boot-primitive installation occur. The environment clearing clears completion values/calls and both global register banks. CPU reset alone does not itself invoke global-slot clearing. This proves those named routes only, not arbitrary reset/memory/card-lifetime guarantees. Sources: `machine/ts/machine/runtime/runtime.ts:58–79`; `machine/cpp/machine/runtime/runtime.cpp:76–107`; `machine/ts/machine/cpu/cpu.ts:869–927,2188–2195`; `machine/cpp/machine/cpu/cpu.cpp:431–482,716–728`.

## Public names installed by base

- ENV05. `base` installs these public names: `next`, `type`, `setmetatable`, `getmetatable`, `rawget`, `rawset`, `getglobal`, `setglobal`, `select`, `error`, `pcall`, `xpcall`, `assert`, `rawequal`, `tostring`, `tonumber`, `print`, `ipairs`, `pairs`. This inventory is the base installer, not an assertion that no other possible cartridge/module can create a global. Source: `machine/bios/base.lua:205–216,219–296`.
- ENV06. `next`, `type`, `setmetatable`, `getmetatable`, `rawget`, `rawset`, `select`, `error`, `pcall`, `xpcall` are assigned the primitive function values first captured in `base` locals. `getglobal` and `setglobal` are direct aliases of the named boot primitives. The other seven names listed in ENV05 are BIOS function definitions. Source: `machine/bios/base.lua:1–12,205–296`.
- ENV07. Boot primitives have their own system-global names; both specs list matching `__bmsx_getglobal`/`__bmsx_setglobal` identities and the paired CPU installers put primitive function values into system-global slots. These private names are evidence, not a recommended public cartridge API. Sources: `machine/ts/spec/blua32/builtin.ts:1–30,40–69`; `machine/cpp/spec/blua32/builtin.h:10–39,49–78`; `machine/ts/machine/cpu/cpu.ts:911–921`; `machine/cpp/machine/cpu/cpu.cpp:475–482`.

## Ordinary globals and library values

- ENV08. Execution images register ordinary and system names into separate banks. A previously unseen ordinary name starts nil; the same ordinary name uses the existing shared bank slot even when another image registers it. Image activation does not overwrite an already existing ordinary slot with nil. Sources: `machine/ts/machine/cpu/cpu.ts:1009–1047,1082–1127`; `machine/cpp/machine/cpu/cpu.cpp:555–591,614–643`.
- ENV09. GETGL reads and SETGL writes an ordinary global slot; GETSYS/SETSYS access the separate system-global bank. These datapaths are slot access, not ordinary Table indexing. Sources: `machine/ts/machine/cpu/cpu.ts:2344–2357`; `machine/cpp/machine/cpu/cpu_dispatch.inl:60–77`. Paired opcode names: `machine/ts/spec/blua32/opcode.ts:56–59`; `machine/cpp/spec/blua32/opcode.h:9–13` plus its included `opcode_list.inl`. **Source-to-opcode name resolution is not established by this sheet; the compiler fact task owns it.**
- ENV10. `getglobal(name)` requires a String name, reads the ordinary bank and returns nil for an absent name. `setglobal(name, value)` requires a String name and writes/creates the corresponding ordinary slot; omitted second argument writes nil. It returns no result values. This is name-based bank access, not a caller-supplied environment Table. Sources: `machine/ts/machine/cpu/cpu.ts:2155–2169,2201–2204,3622–3639`; `machine/cpp/machine/cpu/cpu.cpp:731–739,753–759,1681–1688`; native omitted argument semantics: `machine/cpp/machine/cpu/value.h:326–345`. No disagreement: native `BuiltinArgsView::operator[]` supplies nil for a missing argument.
- ENV11. The installers inspected here do not assign `_G` or `_ENV`; neither is an installed global-environment Table in these sources. Do not instruct readers to use `_G[name]` or replace `_ENV` as a substitute for `getglobal`/`setglobal` on the strength of this sheet. This is a bounded installer/datapath observation, **not** a universal prohibition on a cartridge defining these names, nor a full lexical `_ENV`/loader contract. Sources: complete public installer assignments `machine/bios/base.lua:205–296`; `machine/bios/main.lua:4–23`; ordinary bank implementation in ENV08–10. Source lexical/environment lowering must be verified by the separate compiler task.
- ENV12. The installed `table`, `string` and `coroutine` globals receive library Table values returned by their modules. `table` creates its own Table; `string` adds pattern/format/pack functions to the Table returned by `string/base`, registers that Table for String indexing, and returns it; `coroutine` constructs/returns its Table of wrappers. Sources: `machine/bios/table.lua:1–4,165`; `machine/bios/string/base.lua:1–7`; `machine/bios/string.lua:1–22`; `machine/bios/coroutine.lua:1–40`. API semantics remain in the existing base/protected-coroutine/String/Table references; this fact does not clear the Table STOP.

## Captured dependencies versus mutable public names

- ENV13. Installed BIOS routines do not uniformly re-resolve all public names. `assert` uses locally captured primitive `vm_select` and `vm_error`; `pairs` instead refers to ordinary global `next` when it is called. `print` resolves public `select` and `tostring` in its function body but uses the locally captured console module. `tonumber` refers to public `type` and `error`. Therefore changing a public name must not be described as replacing every use of that operation inside the BIOS. Sources: `machine/bios/base.lua:1–12,219–227,240–260,265–275,294–296`. This fact is about the shown calls, not whole-firmware mutation safety.
- ENV14. A similar distinction exists for the installed String library: `string/base` captures `table.concat` in a local when its module is initialized, while `main` later assigns the public `string` name to the completed module result. `string.lua` registers the actual module Table with the String-index primitive. Reassigning the public `string` name is therefore not, by itself, a new call to that registration primitive. Sources: `machine/bios/string/base.lua:1–5`; `machine/bios/string.lua:1–22`; `machine/bios/main.lua:5–6`. Full String indexing semantics/mutation hazards belong to the canonical String reference, not a new guarantee here.

## Other installed library names; incomplete reference coverage

- ENV15. `math` is installed as the returned Table containing these named fields: `abs`, `acos`, `asin`, `atan`, `ceil`, `cos`, `deg`, `exp`, `floor`, `fmod`, `huge`, `log`, `max`, `maxinteger`, `min`, `mininteger`, `modf`, `pi`, `rad`, `random`, `randomseed`, `round`, `sign`, `sin`, `sqrt`, `tan`, `tointeger`, `type`, `ult`. **Name inventory only**; no domain, precision, error, RNG or timing contract is admitted. Source: `machine/bios/main.lua:12`; `machine/bios/math.lua:349–379`.
- ENV16. `os` is installed as a Table exposing `clock`, `time`, `date`, `difftime`. **Name inventory only**; do not substitute desktop OS/filesystem/process or real-world civil-clock behavior. Source: `machine/bios/main.lua:10`; `machine/bios/os.lua:7,289–333`. A full reference remains a separate facts/author/audit scope.
- ENV17. `lua_compiler` receives a Table containing `compile_syntax`, `syntax_factory`, and `load`; public `load` is assigned that Table's `load` value. The `load` wrapper calls the BIOS load compiler through captured pcall and forwards `source`, `chunk_name`, `mode`, `environment`, `external_scope`, returning its result on success or nil plus error on failure. This is **BIOS runtime compilation**, not evidence for the cartridge/static-require build pipeline. Loader/environment/source-mode/error details have not been fully audited and must not be invented from stock Lua. Sources: `machine/bios/main.lua:8–9`; `machine/bios/compiler/api.lua:1–24`.
- ENV18. The firmware shell's session environment is separately created as an ordinary Table; its session-specific `load` wrapper inserts that Table only when no explicit environment is supplied. It is not the CPU global bank copied wholesale. Keep this observation as a separation boundary, not a chapter API/tutorial unless that scope is separately authored/audited. Source: `machine/bios/shell/repl.lua:1–31,66–80`. Do not conflate this path, public BIOS `load`, the cartridge compiler, or Studio APIs.

## Independent review correction

ENV17 is limited to the `load` wrapper. `compile_syntax` directly exports `load_compiler.compile_chunk` (`machine/bios/compiler/api.lua:4–7`); that path directly calls `compiler.compile` (`machine/bios/compiler/load.lua:27–37`), whose register exhaustion path raises (`machine/bios/compiler/compiler.lua:1942–1945`). Only `load` wraps protection and translates a caught failure to nil plus error (`machine/bios/compiler/api.lua:9–21`). The original frozen extraction is not evidence for interface-wide tuple failures.
