## Language call stack and logical heap: **not byte-RAM allocations**

| ID | Fact | Source lines |
|---|---|---|
| BM30 | A thread retains call frames and a separate value-slot stack initially containing eight slots. TS stack storage is `ValueSlots` (parallel tag/scalar/reference arrays); native stack storage is a vector of guest `Value`. These owners do not assign that storage a guest byte-RAM base. Thus a manual must not invent a top-of-RAM stack pointer or describe these slots as a cartridge-addressable byte array. | `machine/ts/machine/cpu/thread.ts:11-26`; `machine/ts/machine/cpu/value_slots.ts:25-40`; `machine/cpp/machine/cpu/thread.h:15-26` |
| BM31 | Each function frame uses the active thread's value-slot stack: vararg area starts at the previous stack top, register area follows varargs, and reserved register count is at least one and otherwise the function record's max-stack count. Stack top advances past the frame's register area; registers refer to that area. Max-stack is a slot count here, not an absolute RAM stack address. | `machine/ts/machine/cpu/cpu.ts:3175-3183,3220-3236`; `machine/cpp/machine/cpu/cpu.cpp:3017-3028` |
| BM32 | Stack capacity grows to a power-of-two slot capacity, minimum eight; its growth reserves `(newCapacity-oldCapacity)*THREAD_STACK_SLOT_BYTES` against LuaHeap accounting. `THREAD_STACK_SLOT_BYTES=8` and `THREAD_HEAP_BYTES=64` are accounting constants in both mirrors, not proof of an eight-byte physical RAM representation per slot. | `machine/ts/machine/cpu/cpu.ts:523-536`; `machine/ts/machine/cpu/thread.ts:8-9`; `machine/cpp/machine/cpu/cpu.cpp:3419-3425`; `machine/cpp/machine/cpu/thread.h:12-13` |
| BM33 | CPU construction gives LuaHeap the supplied Memory RAM byte count. Both owners calculate a capacity **budget** using supplied count minus `BASE_RAM_USED_SIZE` (`0x80000`, the GEO scratch-size constant). **WITHHELD: unqualified result-equivalence for supplied RAM counts below `0x80000`.** With illustrative count `0x40000`, TS computes `-0x40000`; native unsigned `size_t` computes `2^(bits(size_t)) - 0x40000`. The native width is not frozen here. Do not author a common numerical budget for this input range; supported-product reachability, consumers, installed effects and runtime-fix requirements are unproved. It tracks bytes numerically; these sources allocate no corresponding byte-RAM heap span and do not subtract actual linked DATA/BSS extents. Do not equate this budget with free mapped RAM or place a guest heap at `RAM_BASE+BASE_RAM_USED_SIZE`. | `machine/ts/machine/cpu/cpu.ts:482-490`; `machine/cpp/machine/cpu/cpu.cpp:357-392`; `machine/ts/machine/cpu/lua_heap.ts:16-23`; `machine/cpp/machine/cpu/lua_heap.h:23,41`; `machine/cpp/machine/cpu/lua_heap.cpp:11-14`; constants `machine/ts/spec/bmsx/memory_map.ts:27-30`, `machine/cpp/spec/bmsx/memory_map.h:33-36` |
| BM34 | LuaHeap begins with tracked bytes 0 and a 1 MiB collection threshold. ## Stop conditions / mirror disposition

After independent source audit, paired spec values and the stated bounded reset/EXEC/image-activation, ordinary LOAD_MEM/STORE_MEM, used-value-slot and logical-accounting control-flow facts are accepted only within their specified scope. **WITHHELD: unqualified arithmetic-result equivalence in BM22 for the named overflowing cartridge offset and in BM33 for supplied RAM counts below `0x80000`.** BM27 now restricts zero readback to permitted reads; BM35 guarantees only live-slot clearing, not identical unused-capacity clearing. Audit evidence: `/tmp/bmsx-boot-memory-producer-source-audit.md` and `/tmp/bmsx-boot-memory-cpu-storage-source-audit.md`. These findings do not establish a valid-image, supported-configuration, downstream-effect or runtime-fix claim. Compiler/linker/firmware are their named sole producers; no invented C++ linker mirror or whole-machine parity claim. No tests or runtime edits were made.

## Explicit gaps and narrow next owners

1. **Actual installed RAM capacity / complete cold-reset RAM lifecycle:** not proved. Need the ordinary machine-creation producer that supplies `Memory(ramByteCount,...)` for each supported product, plus the machine reset caller order and Memory reset owner. The model's 4 MiB default and CPU's Memory dependency are not enough.
2. **Usable cartridge byte-RAM span / allocator / hard ownership:** BM01-03 prove linked static placement, not permission to use every byte after cartridge BSS or unused bytes in system/MMIO/GEO reservations. Need the actual cart-facing compiler/linker exported-end/free-storage contract or BIOS byte-buffer allocator if one exists. Do not invent stack/heap/free-RAM fixed endpoints from the map.
3. **Concrete system/cartridge DATA and BSS sizes/base for a shipped ROM:** depend on that exact linked build. No build artifact or symbols were read, so no release-specific numerical cartridge-static base or guessed list of system BSS symbols is supplied.
4. **Declaration syntax, struct field offsets, pointer scaling, array indexing and genuine BLua starter examples:** not fully extracted here. Next named owners: `toolchain/ts/lua/compiler/struct_types.ts`, `toolchain/ts/lua/memory_access_syntax.ts`, the typed-storage compiler paths and actual BIOS examples. Do not infer C/Lua semantics from the spelling `word`.
5. **CPU instruction fetch, execution permission outside ROM, all memory opcode forms and complete faults/IRQ latency:** only ordinary scalar LOAD_MEM/STORE_MEM and boot record binding were inspected. Continue from their named handlers plus mapped-page instruction-fetch owner, COP0 and IRQ leaves; don't generalize the lower Memory scalar rules to every instruction.
6. **Cartridge presence/status/select numeric register contract, banking, permissions, absent-media behavior and slot lifetime/persistence:** firmware literals are not a full device spec. Need mirrored cartridge-controller spec/owner before a public controller section. BM25's slot scan is only firmware behavior.
7. **Boot firmware device state at cartridge entry:** BM26 proves IRQ-mask write and EXEC handoff, not complete GPU/APU/DMA/input latches. Follow only the named BIOS init helpers and affected device owners before saying what a cartridge inherits.
8. **Full BIOS shared-state ownership / terminal VRAM bounds:** BM36 requires `machine/bios/tty/layout.lua` and exact `bmsx/system_assets` texture producer before freezing a numerical reservation. It does not grant use of the rectangle or define when firmware redraws it.
9. **Byte-RAM versus language heap budget interaction / OOM externally visible behavior:** budget accounting is proved, but no physical address aliasing or joint allocator exists in the read owners. Signal-to-user exception routing, GC costs, API visibility (`collectgarbage`, etc.) and object-size accounting for all types remain outside this extraction.
10. **Two simultaneously resident cartridge static sections:** domains 0 and 1 exist, but the linker uses one system-exported cartridge-static base; no concurrent cartridge-RAM allocation/isolation claim is made. Need cartridge-slot invocation/lifetime policy before teaching inter-cartridge execution.

No public chapter should claim these gaps are resolved by this fact sheet.
