## Installed capacity: actual named producers, not just model defaults

| ID | Fact | Source path and line |
|---|---|---|
| ML01 | The mirrored canonical machine model declares main RAM `0x00400000 = 4194304` bytes (4 MiB). The corresponding GPU VRAM field is separately `0x00200000` bytes (2 MiB); it is not part of the main-RAM byte count. | `machine/ts/spec/bmsx/model.ts:27-38,46-57`; `machine/cpp/spec/bmsx/model.h:32-43,51-62` |
| ML02 | The normal browser startup producer supplies the canonical model directly as `machineModel: PSX_MACHINE_SPEC`. The player passes that model to `initializeMachineRuntime`, which passes it to Runtime unchanged. Runtime then constructs Memory with **that model's ramBytes**, not the full 128 MiB address-window size. Thus this ordinary browser construction chain installs 4 MiB main RAM. | `hosts/browser/boot.ts:113-117`; `hosts/browser/player.ts:37-42`; `hosts/common/machine_runtime.ts:13-24`; `machine/ts/machine/runtime/runtime.ts:118-136`; value in ML01 |
| ML03 | The ordinary native LibretroContent producer supplies `PSX_MACHINE_SPEC` directly to RuntimeOptions. Runtime constructs its retained Memory member with `options.machineModel.ramBytes` and supplies that same Memory/model to Machine. Thus this ordinary native construction chain also installs 4 MiB main RAM. | `hosts/libretro/content.cpp:32-49`; `machine/cpp/machine/runtime/runtime.cpp:8-18`; value in ML01 |
| ML04 | RuntimeOptions requires a caller-supplied model; the runtime constructors use its ramBytes. The generic offscreen constructor likewise receives a model and passes it to Runtime. These APIs permit constructing an instance with a supplied model; they do **not** establish a cartridge-selectable RAM profile, guest RAM expansion control or public product configuration menu. The two ordinary product producers in ML02/03 choose the canonical model. | `machine/ts/machine/runtime/options.ts:4-8`; `machine/cpp/machine/runtime/options.h:14-18`; `machine/ts/machine/runtime/runtime.ts:118-136`; `machine/cpp/machine/runtime/runtime.cpp:8-18`; `hosts/common/offscreen_machine.ts:20-28` |
| ML05 | Machine itself takes an already-created Memory dependency; its constructor does not choose/allocate main-RAM capacity. The GPU receives the distinct model VRAM-byte count during Machine construction. This proves the main-RAM versus VRAM allocation boundary, not a CPU-visible VRAM window. | `machine/ts/machine/machine.ts:52-75`; `machine/cpp/machine/machine.cpp:7-23` |
| ML06 | Memory constructor creates exactly the supplied RAM byte count, retained separately from its system-ROM view and I/O-slot array. Its own RAM constructor value-initializes those bytes to zero (`new Uint8Array(count)` / `std::vector<u8>(count)`). This fact is scoped to **fresh Memory backing allocation**, before subsequent device/firmware activity; it is not a cartridge-entry all-zero-RAM guarantee. | `machine/ts/machine/memory/memory.ts:133-162`; `machine/cpp/machine/memory/memory.h:120-127`; `machine/cpp/machine/memory/memory.cpp:90-99` |

With the normal producers' 4 MiB and RAM base `0x08000000`, the backing extent is `[0x08000000,0x08400000)` (last byte `0x083fffff`), before mapped-I/O interception and system-reservation/ownership restrictions. This extent is **not all free cartridge RAM**. | `machine/ts/machine/memory/memory.ts:180-185`; `machine/cpp/machine/memory/memory.h:43-44`; `machine/ts/spec/bmsx/memory_map.ts:6-8`; `machine/cpp/spec/bmsx/memory_map.h:12-14`; producer chain ML01-03 |

## System ROM: supplied byte view, not 16 MiB copied RAM

| ID | Fact | Source path and line |
|---|---|---|
| ML08 | Browser runtime initialization parses the supplied system-ROM bytes, then passes the parsed image's **same bytes** to Runtime. System-image parsing returns the supplied byte view and header; it does not pad/copy it to the 16 MiB ROM window. The native system-image parser likewise returns a span of the supplied pointer/size. Both parsers reject payloads larger than the declared system-ROM window. | `hosts/common/machine_runtime.ts:19-24`; `machine/ts/rompack/image.ts:15-18,24-28`; `machine/cpp/rompack/image.h:16-19`; `machine/cpp/rompack/image.cpp:10-15` |
| ML09 | The native loader opens/maps `bmsx-bios.rom`, parses the mapped bytes, retains the mapped-file member on LibretroContent, and passes `systemRomImage.bytes` to Runtime. This establishes the named retained backing/view chain; it does not freeze the release image's actual byte count. | `hosts/libretro/content.cpp:16,39-45,68-84,118-124`; `hosts/libretro/content.h:19-27` |
| ML10 | Both runtime constructors pass supplied system-ROM bytes to Memory; Memory retains that view (`Uint8Array` / `span<const u8>`) rather than copying it into the RAM array or allocating the full ROM address window. The supplied image length and 16 MiB address window are distinct quantities. | `machine/ts/machine/runtime/runtime.ts:129-135`; `machine/cpp/machine/runtime/runtime.cpp:14-18`; `machine/ts/machine/memory/memory.ts:126-139,157-162`; `machine/cpp/machine/memory/memory.h:26-29,120-125`; `machine/cpp/machine/memory/memory.cpp:90-95`; window constants `machine/ts/spec/bmsx/memory_map.ts:3-4`, `machine/cpp/spec/bmsx/memory_map.h:9-10` |

No guest-callable ROM replacement API is inferred. | `machine/ts/machine/memory/memory.ts:188-193`; `machine/cpp/machine/memory/memory.cpp:102-110`; central sequences ML12-18 |

## Cold construction, central reboot and EXEC are separate edges

| ID | Fact | Source path and line |
|---|---|---|
| ML12 | Runtime construction creates Memory/Machine, clears I/O slots, resets devices, refreshes timing, runs GPU service and applies published GPU timing. The constructor does not itself call CPU reset/boot; boot is a separate call. The central constructor does not reconstruct Memory after device initialization. | `machine/ts/machine/runtime/runtime.ts:118-142`; `machine/cpp/machine/runtime/runtime.cpp:8-26` |
| ML13 | Normal browser and LibretroContent startup call `resetForSystemBoot()` followed by `boot()` after runtime construction. The generic offscreen machine directly calls `boot()` after runtime construction instead. Do not assume every caller uses an identical preparation sequence. | `hosts/browser/player.ts:64-65`; `hosts/libretro/content.cpp:50-53`; `hosts/common/offscreen_machine.ts:26-27` |
| ML14 | `boot()` calls CPU reset, installs boot primitives and marks system entry pending. `rebootSystem()` first calls `resetForSystemBoot()`, then performs those same CPU reset/primitive/entry steps. **Neither method constructs a new Memory** or installs a new system-ROM view. This says which object/lifecycle edge is used; it is not a promise that firmware leaves all byte contents untouched. | `machine/ts/machine/runtime/runtime.ts:68-80,88-91`; `machine/cpp/machine/runtime/runtime.cpp:76-92` |
| ML15 | `resetForSystemBoot()` resets frame/pending-call state, clears I/O slots, calls hardware reset and clears the CPU execution environment. `resetHardwareState()` stops history, resets scheduler and devices/vblank, refreshes timing, runs GPU service and applies published GPU timing. The central methods contain **no bulk main-RAM fill/reallocation** and **no ROM-view replacement**. Device-reset callbacks and subsequent firmware remain separate effects; this is deliberately not a claim of untouched bytes across a complete reboot. | `machine/ts/machine/runtime/runtime.ts:48-66`; `machine/cpp/machine/runtime/runtime.cpp:100-116` |
| ML16 | `Memory.clearIoSlots()` zeros its separate I/O-slot array and clears the bus-fault latch. It does not zero the underlying RAM-byte backing, including RAM bytes at addresses covered by the declared I/O reservation. Clearing I/O slot state is not a main-RAM wipe. The named `Memory.clearMappedPageWriteWatches()` body delegates to the RAM write-watch owner and cartridge controller and contains no direct main-RAM-byte write; the delegated implementations and their transitive effects are not established by this extract. | `machine/ts/machine/memory/memory.ts:136-145,200-202,414-424`; `machine/cpp/machine/memory/memory.h:120-127`; `machine/cpp/machine/memory/memory.cpp:123-126,302-313` |
| ML17 | CPU reset clears execution-stack/residency/transient CPU state, clears mapped write watches, activates/latches the system execution image and pushes the system startup function. `clearExecutionEnvironment()` separately clears completion/call-stack/global-slot state. These named CPU methods contain **no general main-RAM clear or system-ROM installation**. CPU execution of the pushed startup is a later edge. | `machine/ts/machine/cpu/cpu.ts:869-908,923-927`; `machine/cpp/machine/cpu/cpu.cpp:431-472,716-720`; mapped-write-watch effect ML16 |
| ML18 | Successful EXEC clears the active call stack, latches the target execution image/domain, sets entry CPU status, clears its wait/blocked/yield latches and pushes the selected static function. It does **not** call Runtime hardware reset, clear I/O slots, allocate RAM, install ROM or perform DATA/BSS initialization within the EXEC method. Executing a generated startup target can subsequently initialize that image's sections; executing another static function does not implicitly call startup. | `machine/ts/machine/cpu/cpu.ts:1523-1546`; `machine/cpp/machine/cpu/cpu.cpp:1095-1118`; generated startup source ML19 |
| ML19 | Generated startup calls section initialization before static modules and entry. The generated section initializer copies **its own linked image's DATA** from load address to run address, then zeros **its own linked BSS** by word. Thus re-running system/cartridge startup overwrites their DATA/BSS even though the Memory object survives reset/EXEC. No blanket first-entry or warm-entry zeroing guarantee for unrelated RAM follows. | `toolchain/ts/lua/compiler.ts:1505-1584`; own section bases `toolchain/ts/rompack/blua32_linker.ts:1099-1154`; system/cartridge boundaries `1064-1078` |
| ML20 | The named machine device-reset sequence dispatches IRQ, input, DMA, cartridge, GEO, GPU, IMGDEC, GTE, audio, debug-transmit and system resets, in that order. This extraction does **not** expand every device's owned storage or subordinate reset implementation into a general memory-preservation claim. GEO's directly inspected reset clears its register words/job/timing state and mirrors I/O; it does not blanket-clear the declared GEO scratch bytes in that method. | `machine/ts/machine/machine.ts:108-120`; `machine/cpp/machine/machine.cpp:51-63`; bounded GEO method `machine/ts/machine/devices/geometry/controller.ts:237-247`, `machine/cpp/machine/devices/geometry/controller.cpp:125-135` |
| ML21 | The frame loop consumes a pending system reset request by invoking the same `rebootSystem()` path, not by creating another runtime/Memory. Cartridge device reset itself resets selection to zero and calls each inserted card's reset; whether a card's own RAM persists belongs to those card/device owners and is not answered by main RAM's construction behavior. | `machine/ts/machine/runtime/frame/loop.ts:152-158`; `machine/cpp/machine/runtime/frame/loop.cpp:47-52`; `machine/ts/machine/devices/cartridge/controller.ts:123-128`; `machine/cpp/machine/devices/cartridge/controller.cpp:92-97` |

## Directly supported conclusion / publication boundary

- **Confirmed installed main-RAM size for the two named ordinary products:** 4 MiB, because the live browser/native producers pass the canonical model through to Memory (ML01-07), not merely because a default constant exists.
- **Confirmed fresh backing allocation contents:** zero at Memory construction (ML06), not a guarantee about the instant a cartridge begins execution.
- **Confirmed central reset/EXEC object lifecycle:** no new main-RAM backing, no general blanket-RAM clear and no system-ROM-view replacement in the named central bodies (ML12-18). This deliberately does not imply a full reboot preserves all byte values.
- **Confirmed static-section reinitialization:** startup is executable code that copies DATA and clears BSS for its image (ML19). A surviving RAM allocation does not make those contents persistent.

## Gaps / next narrowly named owners

1. **Full memory contents at cartridge entry:** requires delegated device-reset storage effects plus actual BIOS operations before EXEC. The central no-bulk-clear fact cannot establish that a particular scratch byte or buffer survives. Continue only the relevant `Machine.resetDevices()` target and named BIOS writer when a particular region/persistence claim is needed.
2. **Exact shipped system image bytes/length and static extents:** the normal products accept a parsed/loaded image view. This source extraction did not read build artifacts or define a release-specific RAM/ROM byte inventory.
3. **Alternative supported products/profiles:** browser and native libretro ordinary producers are proved. Generic runtime and offscreen constructor injection is proved separately. No exhaustive product list, dynamic RAM profile, capacity-change UI or cartridge-supplied model authority was audited.
4. **Usable/free cartridge bytes and allocation permission:** the 4 MiB backing extent still contains mapped I/O, GEO/system reservations and linked system/cartridge static sections. Neither constructor zeros nor central reset reuse grants allocation ownership. Need the cart-facing static/free-buffer/allocator contract, not a guessed top-of-RAM stack or byte heap.
5. **Save/restore versus reboot:** Memory has independent save-state methods, but whole save-state lifecycle was not part of this extraction. No assertion of persistence across save restore, content reload, process restart or power loss follows.
6. **Cartridge/device RAM persistence:** `CartridgeController.reset()` delegates each inserted card reset. Need the relevant mirrored card plus RAM-device owner before documenting its initialization/reset persistence; main-RAM behavior cannot settle it.
7. **ROM view mutability/ownership outside core:** core retains supplied bytes/span and native content retains mapped-file storage; no claim that an arbitrary external caller cannot mutate a TS source view or replace an installed ROM through other tooling. Public console ROM immutability should derive from the guest memory/access contract, not host-language `const` spelling.
