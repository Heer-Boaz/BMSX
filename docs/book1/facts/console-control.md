## IRQ

| ID | Verified fact and limit | Exact TypeScript source | Exact native source |
|---|---|---|---|
| IRQ1 | The installed CPU, DMA and device assembly shares the IRQ controller. Its three-word interface is FLAGS / ACK / MASK; source raises OR into pending independently of MASK, so repeated pending raises coalesce rather than count events. The asserted maskable line is `(pending & mask) != 0`; reset pending and mask are zero. | Assembly `machine/ts/machine/machine.ts:58-81`; interface `machine/ts/spec/bmsx/io.ts:3-8`; behavior `machine/ts/machine/devices/irq/controller.ts:19-26,72-81`. | Assembly `machine/cpp/machine/machine.cpp:14-23`; interface `machine/cpp/spec/bmsx/io.h:15-20`; behavior `machine/cpp/machine/devices/irq/controller.cpp:14-21,29-34`; line `machine/cpp/machine/devices/irq/controller.h:19`. |
| IRQ2 | FLAGS reads pending without clearing; ACK clears written-one pending bits; MASK writes replace the mask without clearing pending. These operations retain full word bits, not only named-source bits. An aligned mapped whole-word FLAGS write raises READ_ONLY at Memory, before controller dispatch. No subword-access or latency claim follows. | `machine/ts/machine/devices/irq/controller.ts:102-126`; `machine/ts/machine/memory/memory.ts:627-641,852-865`. | `machine/cpp/machine/devices/irq/controller.cpp:72-93`; `machine/cpp/machine/memory/memory.cpp:522-535,729-742`. |
| IRQ3 | CPU maskable acceptance additionally requires current interrupt enable. Accepted maskable delivery enters the image IRQ function with IRQ cause; synchronous exceptions use the system-exception function separately. IRQ is not a count, source-priority selector, all-fault collector, or fixed-latency guarantee. | `machine/ts/machine/cpu/cpu.ts:1680-1683,1718-1739`; bit definitions `machine/ts/spec/blua32/cop0.ts:8,16-24`. | `machine/cpp/machine/cpu/cpu.cpp:2242-2245,2280-2298`; bit definitions `machine/cpp/spec/blua32/cop0.h:14,22-30`. |

## SYSTEM

| ID | Verified fact and limit | Exact TypeScript source | Exact native source |
|---|---|---|---|
| SYS1 | SYSTEM exposes scheduler-cycle-derived TIME_MS and forwards current PCRTC frame-duration / next-VBlank-cycle-budget words. TIME_MS is a cycle-to-millisecond read, not host wall time; frame timing is not an invented fixed refresh value. No scheduler range/exactness, reset origin or physical-clock claim is made here. | `machine/ts/machine/devices/system/controller.ts:86-90,119-137`. | SYS2 | RESET control latches a request and asks CPU to yield; it does not reset hardware within that callback. `takeResetRequest()` consumes the latch; frame-loop consumption calls `rebootSystem()`. Repeated requests can coalesce; no fixed request-to-reboot cycle count follows. | `machine/ts/spec/bmsx/io.ts:414`; `machine/ts/machine/devices/system/controller.ts:139-143,158,300-304`; `machine/ts/machine/runtime/frame/loop.ts:152-158`. | `machine/cpp/spec/bmsx/io.h:427`; `machine/cpp/machine/devices/system/controller.cpp:91-95,110,242-246`; `machine/cpp/machine/runtime/frame/loop.cpp:47-52`. |
| SYS3 | SYSTEM coordinates supervisor entry and fault capture, not a general application-abort register. Declared controls are reset and supervisor enter/leave/fault/publish; supervisor controls are non-user-mode gated. Its supervisor-entry service waits for GPU quiescence, then calls `abortStalledMemoryWrite()` and requests NMI; that CPU abort method only clears the blocked-write latch, not the stored address or frame PC, and proves neither committing nor discarding a store. Fault capture copies CPU cause/EPC/bad-address/Lua-reason/domain words. No complete transition/exception protocol is summarized here. | Controls `machine/ts/spec/bmsx/io.ts:414-418`; gate `machine/ts/machine/devices/system/controller.ts:144-158`; entry `:199-208`; fault copy `:243-249`; abort implementation `machine/ts/machine/cpu/cpu.ts:1654-1656`. | Controls `machine/cpp/spec/bmsx/io.h:427-431`; gate `machine/cpp/machine/devices/system/controller.cpp:96-110`; entry `:151-160`; fault copy `:195-201`; abort implementation `machine/cpp/machine/cpu/cpu.h:285`. |

## INPUT

| ID | Verified fact and limit | Exact TypeScript source | Exact native source |
|---|---|---|---|
| INP1 | Raw input resources: **8 keyboard words / 256 USB HID usage bits**, pointer buttons/X/Y/wheel, and **4 pad records**, each with one buttons word and **6 axes**. The register owner copies these raw snapshot words into the MMIO latches. These are raw states, not guest action mappings or a guarantee that every host supplies every resource. | Spec `machine/ts/spec/bmsx/io.ts:39-50`; contract `machine/ts/machine/devices/input/contracts.ts:3-25,57-76`; latch/publication `machine/ts/machine/devices/input/registers.ts:85-101,121-135`. | Spec `machine/cpp/spec/bmsx/io.h:51-62`; contract `machine/cpp/machine/devices/input/contracts.h:10-34,67-80`; latch/publication `machine/cpp/machine/devices/input/registers.cpp:24-39,59-73`. |
| INP2 | ARM requests one capture at the next accepted VBlank edge: sample, increment sequence, record cycle, consume the pending sample latch, publish latches/status. The retained CTRL word is not cleared by capture. Runtime invokes INPUT on the GPU's VBlank-begin edge. The supervisor request is a separate rising-edge wire checked on every such edge, outside the armed-sample condition; it is not a particular guest key. No independent input polling frequency or event-queue guarantee follows. | `machine/ts/spec/bmsx/io.ts:412-413`; `machine/ts/machine/devices/input/controller.ts:61-100`; VBlank connection `machine/ts/machine/runtime/vblank.ts:44-61`. | `machine/cpp/spec/bmsx/io.h:425-426`; `machine/cpp/machine/devices/input/controller.cpp:31-69`; VBlank connection `machine/cpp/machine/runtime/vblank.cpp:31-45`. |

## IMGDEC

| ID | Verified fact and limit | Exact TypeScript source | Exact native source |
|---|---|---|---|
| IMD1 | Installed decoder resources are **32 input FIFO words**, **64 output FIFO words**, **4096 history words**; words are raw 32-bit values. IMGDEC's DMA request quantum is **16 words**, not a compressed-file size or guaranteed transfer rate. | `machine/ts/spec/imgdec/registers.ts:9-11`; `machine/ts/spec/imgdec/stream.ts:1-2`; allocated owners `machine/ts/machine/devices/imgdec/controller.ts:103-105`; raw FIFO `machine/ts/machine/devices/word_fifo.ts:2,7-9,33-35`. | `machine/cpp/spec/imgdec/registers.h:17-19`; `machine/cpp/spec/imgdec/stream.h:9-10`; allocated owners `machine/cpp/machine/devices/imgdec/controller.h:96-98`; raw FIFO `machine/cpp/machine/devices/word_fifo.h:23-25,54-57`. |
| IMD2 | IMGDEC consumes its compressed **word-token stream** and produces GP0 CPU-to-VRAM upload headers plus decoded texture/optional-CLUT payload into its output FIFO. Eligible DATA reads pop queued output; CPU reads while DMA owns the read port, and empty reads, return the retained DATA word without popping. A programmed DMA transfer can read fixed IMGDEC DATA and write fixed GPU GP0, whose owner accepts DMA words; this is a routed command stream, not a direct IMGDEC→VRAM connection or external PNG/JPEG codec promise. | Stream/header parsing `machine/ts/machine/devices/imgdec/controller.ts:320-352,357-377`; output `:429-483`; DATA `:583-605`; DMA transfer `machine/ts/machine/devices/dma/controller.ts:211-235`; GP0 binding/ingress `machine/ts/machine/devices/gx/gpu.ts:462-464,1034-1052`; upload opcode `machine/ts/spec/gx/gp0.ts:19-20`. | Stream/header parsing `machine/cpp/machine/devices/imgdec/controller.cpp:221-250,258-277`; output `:334-388`; DATA `:491-515`; DMA transfer `machine/cpp/machine/devices/dma/controller.cpp:141-165`; GP0 binding/ingress `machine/cpp/machine/devices/gx/gpu.cpp:53-55,551-569`; upload opcode `machine/cpp/spec/gx/gp0.h:26-27`. |
| IMD3 | The selected model charges **2 system cycles per output word**, including emitted three-word headers; Machine passes that field to IMGDEC, and batch deadlines are `anchor + outputWords * charge`. Payload batches are at most 16 words and limited by output free space, remaining run/stage and available literal input; headers need 3 free words. Service runs due batches and stops scheduling while quiescing. DMA request readiness also depends on input capacity / queued output; GPU destination request depends on its own direction/readiness.
