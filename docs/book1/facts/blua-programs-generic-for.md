## 1. Actual source owners and consumption chain

- Cartridge image building parses Lua assets through `parseLuaChunk`, and its cart branch calls `compileLuaChunkToProgram(..., { programDomain: 'cart', ... })`. The parser wrapper constructs `LuaLexer`, scans tokens, constructs `LuaParser`, then calls `parseChunk`. Evidence: `toolchain/ts/rompack/blua32_image_builder.ts:84–108, 211–224`; `toolchain/ts/lua/analysis/parse.ts:16–21`. The rompacker also directly uses this same lexer/parser for module-dependency discovery: `scripts/rompacker/rombuilder.ts:110–112, 502–514`.
- The compiler builds its semantic frontend from the supplied entry/module ASTs, rejects its diagnostics, and passes `frontend.getFile(...)` directly to `FunctionBuilder`. This is not an independently inferred IDE-only binder contract. Evidence: `toolchain/ts/lua/compiler.ts:5913–5935, 6161–6186, 6301–6313`. Frontend construction consumes `buildLuaSemanticWorkspaceSnapshot`, whose input uses the supplied chunk; bound declaration/reference lookup reads semantic facts keyed by the actual identifier syntax. Evidence: `toolchain/ts/lua/semantic/frontend.ts:157–163, 416–445`; `toolchain/ts/lua/semantic/model.ts:223–244`; `toolchain/ts/lua/compiler/bound_reference.ts:7–26`.
- Statement dispatch reaches `compileForGeneric` for `ForGenericStatement`, and `compileBreak` for `BreakStatement`. Evidence: `toolchain/ts/lua/compiler.ts:3651–3656, 3668–3670`.

## 2. Parsed form and lexical scope

- The accepted generic form has at least one identifier, optionally more comma-separated identifiers, `in`, a nonempty comma-separated expression list, `do`, a block, then `end`. A first identifier followed by `=` takes the numeric-for parser instead. Evidence: `toolchain/ts/lua/syntax/parser.ts:843–869, 1502–1508`.
- Every `in` expression is bound before the binder enters the generic-for loop scope. Only then are all visible loop identifiers declared as active lexical locals, and the body visited; the binder leaves that scope afterward. Consequently a loop name in its own `in` list does not refer to the new loop local, the body uses the loop local, and that local does not become an enclosing-scope binding after the loop. Evidence: `toolchain/ts/lua/semantic/model.ts:952–975, 1665–1681`.
- The loop variables are ordinary local declarations, not constants. The compiler maps each bound declaration to an ordinary local register; its normal assignment-target path permits local writes unless the binding is `const`, and an ordinary local assignment emits `MOV`. Evidence: `toolchain/ts/lua/compiler.ts:4546–4551, 2171–2204, 4090–4102, 4207–4211`.
- Grouping parentheses do **not** create a separate expression node or a one-result barrier here: the parser returns the enclosed expression itself. Any claim imported from stock Lua that `(factory())` necessarily suppresses multireturn would conflict with this parser/compiler pair. Evidence: `toolchain/ts/lua/syntax/parser.ts:1345–1349`; result eligibility below.

## 3. Header expression-list evaluation and cached tuple

- Before the loop's back-edge target, the compiler invokes `compileAssignmentValues(statement.iterators, 3, ...)`, allocates three hidden local registers (iterator, state, control), and fills those registers from the adjusted list. The header expressions are not in the repeated section. Evidence: `toolchain/ts/lua/compiler.ts:4528–4544, 4553–4561, 4580`.
- That assignment-list owner compiles expressions in source order: each expression before the final one is evaluated for exactly one result; the final expression is evaluated afterward. It does not stop evaluating at the target count. Thus surplus header expressions are still evaluated, including their effects/faults, although only the first three adjusted values are copied into the tuple. Evidence: `toolchain/ts/lua/compiler.ts:4159–4204, 4535–4544`.
- Only the final expression can contribute multiple results. It requests the remaining number needed to make three tuple values when that number exceeds one **and** the expression is classified as multireturn; otherwise it requests one. The multireturn classifier accepts varargs and calls, except compiler-resolved `require` module bindings and, at optimization level at least 2, known one-result protos. Evidence: `toolchain/ts/lua/compiler.ts:4178–4203, 5754–5765`. `compileExpressionInto` passes the requested count to calls or emits `VARARG` with that count: `toolchain/ts/lua/compiler.ts:4732–4734, 4749–4751`; the ordinary call emitter writes that requested count into `CALL.C`: `toolchain/ts/lua/compiler.ts:5690–5697`.
- Missing tuple entries are nil. When the final call/vararg is asked for a fixed count, the canonical fixed-result writer/vararg instruction nil-fills absent results; if the adjusted list has no register for an entry, generic-for explicitly loads nil there. Surplus values are ignored by the fixed count / first-three copy. Evidence: `toolchain/ts/lua/compiler.ts:4535–4543`; TS `machine/ts/machine/cpu/cpu.ts:2896–2916, 3406–3438`; C++ `machine/cpp/machine/cpu/cpu_dispatch.inl:475–487`; `machine/cpp/machine/cpu/cpu.cpp:3127–3139`.
- Concrete list-adjustment consequences (derived directly from the cited list owner): one eligible final producer can supply up to all three tuple entries; with two expressions the first supplies one and an eligible second can supply two; with three or more expressions each contributes one to the list, only its first three entries initialize the tuple, and every later expression is still evaluated. A non-multireturn final expression supplies one and the remaining tuple entries become nil.
- These are cached **values**, not deep snapshots. A body/initializer can mutate an object already referenced by a cached value; a register copy preserves its reference rather than copying object contents. Rebinding the original source variable later does not re-evaluate or replace its already cached value. Evidence: generic-for's header-only evaluation/copy `toolchain/ts/lua/compiler.ts:4528–4544`; TS `MOV`/slot copy `machine/ts/machine/cpu/cpu.ts:2309–2311, 3482–3485`; `machine/ts/machine/cpu/value_slots.ts:72–85`; C++ `MOV` and tagged reference construction `machine/cpp/machine/cpu/cpu_dispatch.inl:6–8`; `machine/cpp/machine/cpu/value.h:163–186`.

## 4. Repeated iterator invocation and result adjustment

- Each attempted iteration reloads a call block from the cached iterator, state and control, then emits `CALL` with **exactly two arguments**, state first and control second. There is no implicit receiver or extra argument. Its fixed requested result count is exactly the number of visible loop identifiers, which the parser guarantees is at least one. Evidence: `toolchain/ts/lua/compiler.ts:4553–4561`; `toolchain/ts/lua/syntax/parser.ts:843–854`.
- The operand encoding matters: `encodeFixedCallArgCount(2)` produces `B=3`; fixed `CALL` decodes `B-1` arguments. The generated `C` is the positive visible-variable count, not the open-result sentinel zero. Evidence: `machine/ts/spec/blua32/opcode.ts:70–73`; `machine/cpp/spec/blua32/opcode.h:21–25`; TS call execution `machine/ts/machine/cpu/cpu.ts:2918–2939`; C++ `machine/cpp/machine/cpu/cpu_dispatch.inl:490–503`.
- The ordinary CPU return adjustment supplies exactly that many result slots: extras are dropped and absent results are nil-filled. This applies to closure returns and ordinary builtin results; generic-for adds no independent result validation. Evidence: TS `machine/ts/machine/cpu/cpu.ts:2981–2989, 3406–3438, 3851–3858`; C++ `machine/cpp/machine/cpu/cpu_dispatch.inl:541–545`; `machine/cpp/machine/cpu/cpu.cpp:1876–1892, 3127–3139`.

## 5. Exact termination and body/control order

- The first adjusted iterator result is compared with a nil constant using `EQ A=1`; the following jump exits when equal. It is **not** tested for truthiness. A first result of false therefore continues, is assigned to the first visible local, and becomes the next hidden control value. Nil in a later result does not itself terminate the loop. Evidence: `toolchain/ts/lua/compiler.ts:4563–4571`; TS `EQ` `machine/ts/machine/cpu/cpu.ts:2692–2699` and tag-sensitive equality `3546–3576`; C++ `EQ` `machine/cpp/machine/cpu/cpu_dispatch.inl:341–353` and distinct nil/false encodings `machine/cpp/machine/cpu/value.h:31–39, 125–156`.
- If the first result is nil, execution exits **before** copying any of that call's result slots to visible loop variables, updating hidden control, or running the body. No result means the fixed result writer supplies nil in the first result slot, so the same exit follows. Evidence: ordering `toolchain/ts/lua/compiler.ts:4561–4575`; fixed-return sources in section 4.
- For a nonnil first result, the compiler first copies **all** adjusted results into the visible loop-variable registers, then copies the first visible register into the distinct hidden-control register, then emits the body, then unconditionally jumps back to the iterator-call setup. There is no generic-for increment operation or post-body readback of the first visible variable into control. Evidence: `toolchain/ts/lua/compiler.ts:4568–4580`.
- Assigning a visible loop variable inside the body is an ordinary local-register write and does not change the already copied hidden-control slot. The next successful iteration overwrites visible loop variables from its fresh adjusted result slots. Aliased mutable reference contents are a separate matter from assigning/rebinding a variable; the slot-copy evidence in section 3 applies. Evidence: `toolchain/ts/lua/compiler.ts:4532–4535, 4546–4551, 4568–4571, 4207–4211`.
- A reached `break` targets the nearest active loop context. Generic-for patches its break jumps to the same location after the back-edge instruction as normal nil termination. Thus a reached break skips the remaining body and all subsequent iterator calls; the current iteration's hidden-control copy has already happened before body execution. Evidence: `toolchain/ts/lua/compiler.ts:4621–4627, 4571–4585`; unconditional CPU jump TS `machine/ts/machine/cpu/cpu.ts:2849–2852`, C++ `machine/cpp/machine/cpu/cpu_dispatch.inl:424–426`.

## 6. Reached fault behavior, without duplicating the CPU contract

- Generic-for performs no preflight callable/type check on its cached tuple. After all header evaluation and caching, it attempts the ordinary first iterator `CALL` before any termination decision or body execution. A cached iterator value whose guest tag is neither Closure nor BuiltinFunction faults with `LUA_FAULT_REASON_CALL_NON_FUNCTION` at that reached call; it is not an empty-iteration signal. Evidence: `toolchain/ts/lua/compiler.ts:4528–4566`; TS `machine/ts/machine/cpu/cpu.ts:2918–2939`; C++ `machine/cpp/machine/cpu/cpu_dispatch.inl:490–503`.
- The generic construct passes state/control values directly, including nil/false values, without generic-for-specific argument checks or conversions. A closure receives them through ordinary argument binding, with the CPU's normal parameter/vararg handling; a builtin receives the two argument slots through its normal argument view. Any argument or body fault belongs to the reached operation, not a generic-for header validity pass. Evidence: `toolchain/ts/lua/compiler.ts:4558–4561`; TS `machine/ts/machine/cpu/cpu.ts:3252–3298, 3851–3858`; C++ `machine/cpp/machine/cpu/cpu.cpp:2995–3046, 1888–1892`.
- Narrow concrete argument-fault witness, **not a Table iteration specification**: when the called builtin is Next, its first argument (the cached state in this loop) must have the Table guest tag or the reached builtin raises `LUA_FAULT_REASON_ITERATE_NON_TABLE`. Evidence: TS `machine/ts/machine/cpu/cpu.ts:3599–3603, 4173–4178`; C++ `machine/cpp/machine/cpu/cpu.cpp:1661–1665, 2093–2096`. No Table traversal order, key-validity rule, or mutation policy is established here.
- The source order determines what is reached: a fault while evaluating a later surplus header expression occurs before the first iterator invocation; nil termination prevents the body and next call; a reached break prevents subsequent body instructions/calls. These are control-flow consequences of the cited emission order, not a separate error-recovery mechanism.
